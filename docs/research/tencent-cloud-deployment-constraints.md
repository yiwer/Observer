# Observer 腾讯云单节点部署约束研究

> 研究快照：2026-09-04  
> 范围：中国大陆地域、中国香港地域及其他境外地域；单节点 CVM/Lighthouse、邮件投递、OpenAI/Anthropic/GitHub 官方 API、COS 与备份。  
> 证据边界：仅使用腾讯云、工信部、国家网信办、OpenAI、Anthropic、GitHub 官方一手资料。未创建计费资源，未调用收费 API，未做端口探测、连通性测试、VPN/代理或其他网络绕过。  
> 本文是产品与架构研究，不是法律意见。

## 结论先行

如果 Observer V1 必须由单节点直接调用 OpenAI 和 Anthropic 第一方 API，那么腾讯云中国大陆和中国香港都不是低风险地域：截至本研究日，两家的官方 API 支持地域清单均列有新加坡、日本和台湾，但都没有列出中国大陆或中国香港。OpenAI 明示在清单外访问或提供访问可能导致账户被封禁或暂停；Anthropic 除地域清单外，还对由不支持地区主体多数控制的企业/组织设置了跨地域限制。[OpenAI API 支持地域](https://developers.openai.com/api/docs/supported-countries)；[Anthropic 支持地域](https://www.anthropic.com/supported-countries)；[Anthropic 2025 年地域限制公告](https://www.anthropic.com/news/updating-restrictions-of-sales-to-unsupported-regions)

在“运营者和 API 账户本身确实满足供应商地域/所有权政策”这一前提下，腾讯云新加坡或东京是比大陆、香港更合适的 V1 候选。新加坡可作为首选起点，东京作为同级备选；这不是对中国大陆访问质量的保证。腾讯云明确提示，从中国内地跨境访问香港或其他境外地域可能出现较大延迟和丢包。[腾讯云 Lighthouse 地域与网络连通性](https://cloud.tencent.com/document/product/1207/50103)

如果运营者、付款主体或组织所有权不满足供应商政策，把服务器搬到新加坡也不能自动解决账户合规问题，尤其不能绕过 Anthropic 针对中国控制实体的限制。此时低风险做法是删除对该第一方 API 的硬依赖，或先取得供应商书面确认，而不是使用代理、转售账户或网络绕过。

另一个比选区更早的门槛是“日报是否面向社会公众”。公开提供由 AI 选择、编辑、摘要并发布的新闻，存在被认定为互联网新闻信息转载服务的明显可能；ICP 备案不等于取得互联网新闻信息服务许可。V1 最低风险边界应是单用户、自用、强鉴权、无公开注册、无公开新闻门户、无公开应用商店分发，并在扩展为公众服务前完成专项合规判断。[国家网信办许可实施细则](https://www.cac.gov.cn/2017-05/22/c_1121015789.htm)

## 地域决策矩阵

| 约束 | 腾讯云中国大陆 | 腾讯云中国香港 | 腾讯云新加坡/东京 |
|---|---|---|---|
| 中国大陆 ICP | 公网网站/APP 在开通前需备案；域名和仅 IP 访问都在法规范围内 | 源站自身不要求中国大陆 ICP | 源站自身不要求中国大陆 ICP |
| 大陆 CDN/全球 CDN | 已备案域名才能接入 | 一旦使用中国境内或全球加速，ICP 要求重新出现 | 一旦使用中国境内或全球加速，ICP 要求重新出现 |
| OpenAI 第一方 API | 官方清单未列出；不应部署为直接依赖 | 官方清单未列出；不应把“香港”当成已支持境外地域 | 新加坡、日本均在官方清单；仍需核实账户、运营者及下游提供方式 |
| Anthropic 第一方 API | 官方清单未列出；中国控制实体另有跨地域限制 | 官方清单未列出；服务器搬到香港不能消除实体限制 | 新加坡、日本均在官方清单；但中国控制实体限制仍可能使其不可用 |
| GitHub 官方 API | 官方资料未给出中国大陆禁用项，但也没有大陆网络可达性/SLA 保证 | 未见香港特定禁用项 | 未见新加坡/日本特定禁用项 |
| 大陆用户访问质量 | 通常最接近大陆用户，但不改变境外 API 政策 | 跨境链路可能延迟或丢包 | 跨境链路可能延迟或丢包 |
| SMTP 25 | CVM 默认封禁；Lighthouse 不支持解封 | 同一腾讯云实例产品限制仍需遵守 | 同一腾讯云实例产品限制仍需遵守 |
| 公众新闻/Android 合规 | ICP、APP 备案、新闻许可可能同时成为门槛 | 不需大陆源站 ICP，不代表面向大陆公众的 APP/新闻业务当然免许可 | 与香港相同，且还需遵守部署地当地法律 |

矩阵中的“未列出”来自对供应商当前完整公开清单的核对，不代表对未来政策的永久判断。

## 1. 中国大陆公网网站/API：备案不是按端口判断

### 1.1 域名和纯 IP 都在法规范围内

工信部《非经营性互联网信息服务备案管理办法》第五条规定，在中国境内提供非经营性互联网信息服务应履行备案；其定义同时覆盖“通过互联网域名访问的网站”和“仅能通过互联网 IP 地址访问的网站”。因此，把 Observer 称作 REST API、改用非 80/443 端口，或长期以公网 IP 提供下载和同步，都没有官方豁免依据。[工信部《非经营性互联网信息服务备案管理办法》](https://www.miit.gov.cn/gyhxxhb/jgsj/cyzcyfgs/bmgz/xxtxl/art/2024/art_84a0cfa0ebd049bbbe751dca9a008e56.html)

腾讯云平台文档也明确：托管在中国境内服务器的网站或 APP 需要备案，判断不取决于端口；域名解析到腾讯云中国境内资源前必须完成备案，否则会被未备案监测拦截。腾讯云允许在域名未解析时通过公网 IP 暂时测试，但这只是测试期平台操作说明，不能覆盖工信部对长期纯 IP 信息服务的定义。[腾讯云：是否需要备案](https://cloud.tencent.com/document/api/243/19630)

据此，V1 的产品边界应写成：

- 本地或短期 IP 测试不等于生产上线资格。
- 大陆节点上的公开 API、MD/PDF 下载、管理页和 Android 同步接口应统一纳入备案设计。
- 若域名已经在其他接入商备案，迁入腾讯云大陆资源仍需办理腾讯云接入备案；已有备案号不等于已经完成腾讯云接入。[腾讯云：接入备案相关](https://cloud.tencent.com/document/faq/243/43878)

### 1.2 备案会改变采购和域名计划

腾讯云当前要求，可用于其备案的 CVM/Lighthouse 必须是中国境内资源、包年包月、累计购买至少 3 个月、有公网 IP 且带宽不为 0；中国香港和境外资源无需备案，也不能充当大陆备案资源。[腾讯云：备案云资源](https://cloud.tencent.com/document/product/243/18908)

域名需要实名认证，备案主体、域名实名主体及服务器接入关系必须按管局和腾讯云规则准备。因而若选择大陆节点，域名、主体身份和至少 3 个月的合格云资源不是上线后的补办项，而是发布前依赖。

### 1.3 境外源站加大陆节点，ICP 要求会回来

腾讯云 CDN 的加速区域若选“中国境内”或“全球”，域名必须先完成 ICP 备案；只选“中国境外”时不要求大陆 ICP。[腾讯云 CDN 使用限制](https://cloud.tencent.com/document/product/228/37848)

因此：

- 香港/新加坡源站 + 仅境外 CDN：不因源站本身产生大陆 ICP 前置条件。
- 香港/新加坡源站 + 中国境内或全球 CDN：需要已备案域名。
- 境外源站回源到大陆 CDN 仍涉及跨境链路；腾讯云明确表示无法保证这种回源效果。[腾讯云 CDN 源站配置](https://cloud.tencent.com/document/product/228/41334)

不能把“先上香港、后开大陆 CDN”当成无需备案的平滑升级路径。

同时，“不需要中国大陆 ICP”不等于没有部署地义务。腾讯云境外服务协议要求用户遵守服务所在境外地区的资质、实名认证、数据隐私等当地要求；具体义务取决于实际地域和业务。[腾讯云：购买/使用境外服务协议](https://cloud.tencent.com/document/product/301/92985)

## 2. ICP 之外：Android APP 与新闻服务许可

### 2.1 Android 公开发行有独立 APP 备案轨道

工信部规定，在中国境内从事互联网信息服务的 APP 主办者应履行 APP 备案；新 APP 应先备案再开展业务，应用分发平台也参与备案核验。[工信部关于开展移动互联网应用程序备案工作的通知](https://www.miit.gov.cn/zwgk/zcwj/wjfb/tz/art/2023/art_920db564162e4312916a01bed6540ad8.html)

服务器位于香港或新加坡，不能单独推出“Android 客户端必然不需 APP 备案”的结论。自用侧载 APK、受邀请的单用户客户端与面向社会公众上架是不同场景，必须由用户明确选择。若 V1 不含 Android 客户端，也应从第一版 API 设计保留鉴权和版本化，而不提前宣称未来上架免备案。

### 2.2 “新闻日报”可能触发更高层级许可

国家网信办实施细则规定，通过网站、应用程序等向社会公众提供互联网新闻信息服务应取得许可；服务类别包括采编发布、转载和传播平台，其中“转载服务”包含选择、编辑并发布其他主体已经发布的新闻信息。[国家网信办：互联网新闻信息服务许可管理实施细则](https://www.cac.gov.cn/2017-05/22/c_1121015789.htm)

Observer 的“跨来源采集 → AI 筛选 → 摘要/分析 → 邮件、网页或 APP 发布”与该定义存在显著交集。具体是否落入许可范围取决于公开性、服务对象、新闻类别、编辑行为、来源和运营主体，应由合格专业人员判断。架构上至少要做到：

- V1 不开放公众注册，不提供可索引的公共新闻门户，报告 URL 默认私有。
- 邮件只发给明确配置的单一或封闭收件人，Android 采用配对/鉴权。
- 所有条目保存来源、原链接、抓取时间、事实与 Agent 分析边界。
- 扩展公众订阅前，把互联网新闻信息服务许可评估设为发布门禁；不要把 ICP 备案通过视作充分条件。

腾讯云备案指南也提示，新闻、出版等互联网信息服务可能需要前置审批文件。[腾讯云：如何快速备案网站或 APP](https://cloud.tencent.com/document/product/243/39038)

## 3. OpenAI、Anthropic、GitHub：地域、账户和网络是三个不同问题

### 3.1 OpenAI

OpenAI 官方页面称其清单为“当前支持访问 API 服务的国家和地区”，并明确在清单外访问或向清单外提供访问可能导致账户被封禁或暂停。截至 2026-09-04，完整清单列有 Singapore、Japan、Taiwan，未列出 China 或 Hong Kong。[OpenAI API 支持国家和地区](https://developers.openai.com/api/docs/supported-countries)

Codex CLI 可以使用 ChatGPT 订阅登录，也可以使用 API key；官方特别建议程序化 CLI/CI 工作流使用 API key，并说明两种方式适用的管理和数据政策不同。因而，Observer 若以 API key 在云端运行 `codex exec`，上述 API 地域清单直接构成上线门槛；若改用 ChatGPT 登录或企业 access token，则是另一套身份与产品政策边界，不能把 API 清单的结论机械外推，仍需按实际认证方式确认资格。[OpenAI Codex 身份验证](https://learn.chatgpt.com/docs/auth)

架构结论：

- 腾讯云大陆或香港节点不能作为 OpenAI 第一方 API 的合规默认部署。
- 新加坡或东京节点只解决“工作负载出口所在地域”这一维；官方页面没有在同一文档中说明运营者居住地、付款主体、账户注册地，以及“在支持地域生成日报后交付给大陆用户”是否构成向清单外提供访问。
- Observer 是生成成品日报而不是转售模型接口，但不能据此自行解释供应商政策；上线前应取得适用于实际账户和服务方式的书面确认。

### 3.2 Anthropic

Anthropic 的当前商业 API 支持清单列有 Singapore、Japan、Taiwan，未列出 China 或 Hong Kong。该页面还保留对多数直接或间接所有权来自非支持国家之实体拒绝提供服务的权利。[Anthropic 支持国家和地区](https://www.anthropic.com/supported-countries)

Claude Code 的官方安装前置条件也明确要求运行位置位于 Anthropic 支持国家/地区。因此，在服务器上使用 `claude -p` 并不存在脱离地域清单的 CLI 例外；运行位置、认证方式和账户/组织资格需要同时成立。[Claude Code：系统要求](https://code.claude.com/docs/en/getting-started)

2025 年公告进一步明确：由不支持地区（公告举例为中国）控制的企业或组织，即使通过在其他国家设立的主体运营，也受强化后的限制；公告将“由不支持地区总部企业直接或间接持股超过 50%”列为包含情形。[Anthropic：Updating restrictions of sales to unsupported regions](https://www.anthropic.com/news/updating-restrictions-of-sales-to-unsupported-regions)

因此：

- 大陆节点和香港节点均不是 Claude 第一方商业 API 的低风险入口。
- 中国控制的公司/组织不能仅靠把 CVM 放到新加坡来解决资格问题。
- 对个人自用账户、个人与未来公司主体之间的边界，公开材料不足以替 Observer 作最终判断；应向 Anthropic 书面确认。
- Anthropic 的位置说明明确区分消费产品（包括 Free/Pro/Max 账户使用 Claude Code）与商业 API；不能把消费产品页面的可用性直接推导成商业 API 资格。该页面还说明会以 IP 等信号推断大致地域以执行条款与反滥用。[Anthropic Privacy Center：位置使用](https://privacy.claude.com/en/articles/11186740-does-claude-use-my-location)

### 3.3 GitHub

GitHub 官方贸易管制页面强调在适用法律和美国出口/制裁规则范围内尽可能提供全球访问；当前列举的受制裁地域不包含中国大陆或中国香港。GitHub 会结合 IP 和付款历史判断受贸易限制账户，但官方页面不是一份逐国网络可用性或 SLA 清单。[GitHub and Trade Controls](https://docs.github.com/en/site-policy/other-site-policies/github-and-trade-controls)

本次官方资料检索没有找到 GitHub 对“腾讯云大陆地域访问 api.github.com”的可达性、时延或稳定性保证。故可确认的是账户必须遵守贸易管制和 API 条款，不能确认大陆跨境网络始终可达。

新闻采集层应按 GitHub 官方约束实现，而不是把一次连通当成生产保证：

- 公共数据未认证调用的主限额为 60 次/小时；认证用户通常为 5,000 次/小时。
- 搜索端点另有限额；REST 与 GraphQL 还有次级限流。
- 应使用认证、条件请求、ETag、缓存、串行队列及 Retry-After/指数退避。[GitHub REST API 限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)；[GitHub REST API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

### 3.4 不做“网络能通所以允许”的推断

腾讯云只要求实例访问“合规的境外网站”；其 VPN 产品明确不提供 Internet 访问或代理能力，并禁止用技术方式绕过网络审查。[腾讯云 CVM 实例限制 FAQ](https://cloud.tencent.com/document/faq/213/17279)；[腾讯云 VPN 场景 FAQ](https://cloud.tencent.com/document/faq/554/79786)

所以本项目不得把以下方案写入 V1：

- 在大陆节点上用 VPN、代理或非官方转发绕过供应商地域规则。
- 购买或共享他人 API 账户、复用个人订阅 OAuth 向服务端用户提供代理。
- 以一次 curl/浏览器测试成功替代供应商支持地域、账户资格和网络 SLA。

## 4. 腾讯云 SMTP 25/465/587 与 SES

### 4.1 实例出站端口

| 产品/端口 | 官方边界 | Observer 决策 |
|---|---|---|
| CVM TCP 25 | 默认封禁访问外部 25；仅预付费包年包月 CVM 可申请解封，按量付费不支持 | 不依赖解封 |
| CVM 解封后的 25 | 只能连接第三方 SMTP 中继；若直接由 CVM 用 SMTP 外发，腾讯云可永久封禁 | 不自建 MTA，不做 direct-to-MX |
| Lighthouse TCP 25 | 默认受限且不支持解封 | Lighthouse 不能承担 25 端口发信 |
| 465/587 | 所查腾讯云文档没有声明平台统一封禁；CVM 文档推荐 465，腾讯云 SES 服务端支持 465/587 | 这不是任意邮件端点均可达或具备 SLA 的承诺；仍需配置安全组/主机防火墙，并在非生产环境验收所选端点 |

腾讯云明确建议优先使用其他端口，并指向 465 方案。[腾讯云 CVM：解封 25 端口](https://cloud.tencent.com/document/product/213/40436)；[腾讯云 Lighthouse：常见问题](https://cloud.tencent.com/document/faq/1207/44569)；[腾讯云 Lighthouse：管理实例防火墙](https://cloud.tencent.com/document/product/1207/44577/)

因此 V1 邮件路径应是：

1. 首选 HTTPS 邮件 API；
2. 其次是经过认证的 SMTP submission；优先采用腾讯云明确推荐的 465，若选 587 则先验收目标服务端点；
3. 明确禁止节点自行运行 MTA 经 25 端口直投收件方 MX。

### 4.2 腾讯云 SES 的端口与账号限制

腾讯云 SES 当前中国站 SMTP 地址区分香港、广州和国际站，官方端口表列出 25、465、587；25 为 STARTTLS，465 为隐式 SSL/TLS。[腾讯云 SES：SMTP 服务地址](https://cloud.tencent.com/document/product/1288/65750)

即使 SES 服务端支持 25，CVM/Lighthouse 的出站规则仍使 25 不适合作为设计依赖；使用 465 或 587。

2026-03-02 起新开通 SES 的个人实名认证用户不再支持 SMTP 发信，官方建议升级企业认证或使用 API/控制台。SMTP 的当前限频为同一 appId 20 次/秒、同一发件人到同一收件人 10 次/小时。[腾讯云 SES：SMTP 发送邮件指南](https://cloud.tencent.com/document/product/1288/65749)

这意味着：

- “腾讯云个人账号 + SES SMTP”不能作为必然可用的 V1 假设。
- 单用户每日一封远低于频率上限，但必须先确定账号认证类型。
- 若用第三方 SMTP，也必须使用第三方允许的 465/587 和独立凭证。

### 4.3 SES API 不是零配置邮件出口

SES 要求拥有并验证发信域名，保持 SPF、DKIM、DMARC 等 DNS 记录；仅作发信用途的域名不强制 ICP，但若其 A 记录指向大陆服务器，则仍需备案。[腾讯云 SES：身份验证和配置](https://cloud.tencent.com/document/product/1288/60652)；[腾讯云 SES：域名相关问题](https://cloud.tencent.com/document/faq/1288/52776)

当前 SendEmail 文档还有以下架构影响：

- API 的业务 Region 只支持 ap-guangzhou 和 ap-hongkong；其他地域化域名是 API 接入点，不等同于产品实际服务地域。
- 默认只支持使用审核通过的模板发信；模板不能全部由变量组成，`TemplateData` 变量值不能直接传入 HTML 或复杂结构，因此完整动态日报不应假定能作为模板变量发送。[腾讯云 SES：模板相关问题](https://cloud.tencent.com/document/faq/1288/52777)；[腾讯云 SES：发送功能相关问题](https://cloud.tencent.com/document/product/1288/52778)
- 请求包最大 8 MB；附件经 Base64 膨胀，官方建议附件原始总量控制在 4 MB 以内。
- 默认接口频率 20 次/秒，投递还受域名信誉、日额度、退信和投诉控制。[腾讯云 SES：发送邮件](https://cloud.tencent.com/document/product/1288/51034)；[腾讯云 SES：请求结构](https://cloud.tencent.com/document/product/1288/51055)；[腾讯云 SES：发送限制相关问题](https://cloud.tencent.com/document/product/1288/52775)

对 Observer 的推荐是“已审核固定模板 + 今日总览 + 私有短期签名链接”，而不是默认把每天变化的整篇日报塞入模板变量；PDF 仅在确定小于附件预算时附加。若必须发送完整动态 HTML，需先确认 SES 模板能力与审核边界，或使用具备企业认证资格的 SMTP 465 路径。

邮件 API 返回成功只表示服务商受理，不等于收件箱在 08:30 前可见。必须记录 provider message id、投递回调和最终状态；生成报告成功不能因邮件失败而回滚删除报告。若“08:30 前送达”是硬承诺，应以服务端私有报告在 08:30 前可读取作为可控验收点，把邮件定义为交付副本而非唯一可用性证明。

## 5. 单节点 Docker、COS、备份与时区：只保留设计门槛

### 5.1 单节点是被接受的单点故障

Docker Compose 可以承载 V1，但必须在产品承诺中明确：

- 没有自动故障转移，也不能称为高可用。
- 进程重启后能幂等补跑，避免同一期重复发信。
- 抓取、生成、渲染、归档、发信分别持久化状态；失败可从最近成功阶段续跑。
- 发布截止前预留重试窗口；节点在截止后恢复时按既定规则生成“延迟版”或记录缺刊。
- 密钥不写入镜像、Compose 文件、报告、日志或普通备份。

### 5.2 报告和备份必须离开计算节点

至少把数据库逻辑备份、配置版本、原始来源清单、MD/PDF 成品和发布状态写到私有 COS。CVM/Lighthouse 与 COS 应优先同地域，以使用同地域内网；跨地域默认不能以内网访问。[腾讯云 Lighthouse 地域与网络连通性](https://cloud.tencent.com/document/product/1207/50103)

建议开启 COS 版本控制和生命周期策略；是否增加跨地域复制由 RPO/RTO 决定。跨地域复制是异步的，完成时间可能从几分钟到数天，并会产生请求、目标存储和跨地域流量费用，不能宣称零 RPO。腾讯云当前还明确说明不同账号的存储桶不能互为复制源和目标，因此“跨地域复制”也不能自动满足“跨账号隔离”。[腾讯云 COS：版本控制](https://cloud.tencent.com/document/product/436/19884)；[腾讯云 COS：存储桶复制概述](https://cloud.tencent.com/document/product/436/19237)

### 5.3 快照不能替代数据库一致性备份

腾讯云说明，快照只捕获已经写入磁盘的数据，内存缓冲区不会进入快照；数据库写入期间的快照可能漏掉新数据，应先受控停止写入/刷盘，或使用数据库原生一致性备份。[腾讯云云硬盘：创建快照](https://cloud.tencent.com/document/product/362/5755)

跨地域复制云硬盘快照不支持系统盘快照，且该功能已经商业化。[腾讯云云硬盘：跨地域复制快照](https://cloud.tencent.com/document/product/362/18152)

Lighthouse 的快照只覆盖系统盘，销毁实例时会同步删除该实例全部快照，因此不能作为唯一备份。[腾讯云 Lighthouse：管理快照](https://cloud.tencent.com/document/product/1207/48546/)

最低验收门槛不是“备份任务成功”，而是能从节点外备份恢复数据库、报告索引和至少一份完整日报。

数据库引擎尚未确定，因此不能预先把某一种腾讯云数据库备份产品写成通用答案。腾讯云 DBS 当前公开的逻辑备份范围主要是 MySQL、MariaDB、Percona 和 TDSQL-C MySQL；自建 PostgreSQL 或 SQLite 仍需使用数据库原生的一致性备份工具，再把产物写到节点外。[腾讯云 DBS：备份和恢复能力](https://cloud.tencent.com/document/product/1513/64026)；[腾讯云 DBS：准备工作](https://cloud.tencent.com/document/product/1513/64040)

### 5.4 时区由应用显式定义

设计门槛：

- 所有持久化时间使用 UTC。
- 日报业务日期、07:30 等截稿/发布时间显式使用 Asia/Shanghai。
- 覆盖窗口保存起止时间和时区，不依赖宿主机默认时区。
- 重启补跑以“业务日期 + Edition + 版本号”作为幂等键，而不是只看 cron 是否执行。

## 6. 推荐的低风险 V1

### 推荐方案：有条件的新加坡单节点、私人自用

前提条件：

1. OpenAI 账户、付款主体、实际运营者和服务交付方式已被确认符合其地域政策。
2. 若启用 Anthropic，个人/组织及所有权结构已被确认符合其地域政策；中国控制实体不能把服务器地域当作规避手段。
3. Observer V1 是单用户、自用、强鉴权、非公开订阅、非应用商店公开发行。

部署轮廓：

- 腾讯云新加坡 CVM 或 Lighthouse 单节点；东京是同级备选。
- 私有同地域 COS 保存报告与节点外备份。
- 模型、新闻源、GitHub、邮件全部通过 provider adapter 接入，任何单一境外 API 都不能阻塞归档。
- 邮件优先走腾讯云 SES HTTPS API 或合规第三方邮件 API；若用 SMTP，只用 465/587。
- 公网只暴露 HTTPS，报告采用短期签名 URL；管理入口与 Android API 均鉴权。
- 调度显式使用 Asia/Shanghai，状态和审计时间使用 UTC。
- 接受单节点故障和大陆跨境访问波动，以自动补跑、离线报告和邮件为降级路径。

选择新加坡不是因为它对大陆网络一定优于香港，而是因为新加坡同时出现在 OpenAI 和 Anthropic 当前 API 支持清单中，而香港不在。实际账户资格与对大陆用户交付的政策解释仍需供应商确认。

### 不推荐的两个默认方案

**大陆单节点 + 直接调用 OpenAI/Anthropic**：供应商支持地域不匹配，同时增加 ICP、可能的 APP 备案和新闻许可门槛。不能以连通性实测或代理补齐。

**香港单节点 + 直接调用 OpenAI/Anthropic**：虽然不需大陆源站 ICP，但香港没有出现在两家的当前 API 支持清单中；它不是该问题的合规折中。

### 何时改选香港或大陆

- 如果删除 OpenAI/Anthropic 第一方 API 硬依赖，并接受大陆跨境访问波动，香港可作为无大陆源站 ICP 的候选。
- 如果稳定服务大陆公众比第一方境外模型更重要，应改用对大陆运营者和大陆工作负载有明确官方支持的模型/信息服务，完成 ICP、APP 备案及新闻许可评估后再选大陆地域。
- 如果既要大陆稳定访问，又要境外第一方 Agent，单节点约束很可能需要放宽为“境外采集/生成节点 + 大陆合规交付节点”；这已超出本报告的单节点 V1。

## 7. 已确认前提与仍需决策

本轮需求澄清已经确认：V1 为单用户私人服务；腾讯云单节点部署，不承诺高可用；Markdown 是规范正文，PDF 是派生渲染；不设人工编辑后台，兴趣偏好使用配置文件；Android 覆盖无 GMS 手机且不做通知，由客户端打开时主动同步。上述事项不再作为地域选择的待答问题。

上线前仍需决定或取得外部确认：

1. **实际主体与账户资格**：运营者、付款主体和账户注册地是什么；若启用 Anthropic，其组织所有权限制是否适用？
2. **供应商书面确认**：OpenAI/Anthropic 是否允许以该账户在支持地域后台生成，并向中国大陆单一用户交付成品日报？公开资料不足以代替逐案确认。
3. **地域批准**：是否接受“腾讯云新加坡为首选、东京为备选”；若账户资格不成立，是否同意删除相应第一方 Agent 硬依赖，而不是退回大陆/香港或使用绕过方案？
4. **Agent 降级策略**：Codex 与 Claude 是两个可替换 runner，还是必须同时可用；两者均不可用时，是按确定性采集结果生成降级版，还是记录缺刊？
5. **邮件路径与账号类型**：使用腾讯云中国站还是国际站账号、个人认证还是企业认证；是否采用推荐的 SES HTTPS API 固定模板 + 私有链接，还是确有完整 HTML 邮件需求而选择企业 SMTP 465？
6. **08:30 验收语义**：是服务端报告已发布、邮件服务商已受理，还是收件箱实际可见；邮件系统无法独立证明最后一项。
7. **PDF 交付**：PDF 必须作为附件，还是接受正文 + 私有签名下载链接；若附件，是否接受原始附件总量不超过约 4 MB 的设计预算？
8. **大陆访问与恢复目标**：是否接受境外单节点到大陆的偶发延迟/丢包；数据库采用什么引擎以及自建还是托管；RPO/RTO 各是多少，是否需要跨地域副本以及另行设计跨账号隔离？
9. **未来扩展门禁**：Android 公开上架或服务开放给公众属于 V1 之外的独立决策；进入该阶段前，是否接受 APP 备案与互联网新闻信息服务许可专项评估作为强制门禁？

## 8. 官方资料仍未确认的事项

- 腾讯云大陆 CVM 到 api.openai.com、api.anthropic.com、api.github.com 的长期网络可达性、时延和 SLA；本研究没有进行连通性测试。
- OpenAI 支持地域页面对账户注册地、付款主体、组织所有权，以及“交付成品给清单外用户”的精确定义。
- Anthropic 对中国大陆个人自用者、非公司组织及不同所有权结构的逐案处理。
- GitHub 是否对中国大陆网络提供特定可用性承诺；官方贸易管制页面不能替代网络 SLA。
- 私人、单用户 AI 日报是否落入互联网新闻信息服务许可；官方没有针对 Observer 这种产品形态的专门豁免。
- 实际腾讯云账号能获得的 SES 日额度、模板能力、SMTP 权限和 IP 白名单；这些需在账户内确认，未开通或试发。
- 香港、新加坡、东京到目标中国大陆运营商的真实访问质量；腾讯云只给出跨境可能高延迟/丢包的边界，没有给出 Observer 场景的保证。

这些未知项不应通过网络绕过、借用账户或先公开上线来“验证”，而应通过供应商书面确认、合规评估和非生产验收解决。

# Observer 产品需求文档（PRD）

版本：1.0 · 日期：2026-09-05 · 范围：V1 服务端与 Phase 2 客户端边界

产品决策：Q1–Q75 及整体共享理解已由 Owner 确认。本文按 to-spec 模板整理；T1 测试边界已随 V1 ticket 拆分获 Owner 确认，具体技术选型和实测结果不冒充已确认事实。Issue tracker 发布状态另行记录。

## Problem Statement

Owner 希望持续了解全球的重要变化，但新闻分散于媒体、机构公告、论文、社交平台和开源项目，手工搜索与阅读耗时。同一事件在多个来源反复出现，营销声明、未验证消息和分析常与事实混在一起；热门开源项目也容易连续多天占据榜单，使每天阅读缺少新增价值。

Owner 已能使用 coding agent，希望将它们的检索、材料处理、核验与写作能力应用于自动日报。成功的产品必须在固定时间提供有来源、分主题、可归档的中文内容，失败时说明缺口，发现错误后留下更正记录。阅读介质既包括邮件，也包括未来无 GMS 的 Android 手机；Markdown 和 PDF 应保持内容一致。

目标用户是唯一的 Owner，同时承担私人服务运维和来源配置维护。当前没有多租户、公开运营或商业分发需求。

## Solution

构建私人每日简报服务 Observer：持续收集经批准的来源，形成有时间与证据记录的候选池，交给可替换的 Codex/Claude Research Agent 完成核验、选题和分析，再生成版本化 Daily Brief。

一份 Daily Brief 包含以下六个 Edition，以及用于导航的 Today Overview：

| Edition | 主要内容 | 编辑边界 |
|---|---|---|
| 世界要闻 | 地缘政治、战争外交、选举政策、灾害、公共卫生、气候、人道事件 | 重大全球/区域影响优先；冲突和数字要求更严格核验 |
| AI 日报 | 模型、研究评测、产品、开发工具、基础设施、安全治理、版权与应用 | 能力和生态变化优先；不把营销声明写成独立验证结果 |
| 财经日报 | 宏观、央行监管、财报、并购资本事件、供应冲击、合规收盘背景 | 无实时行情、个性化持仓分析或交易建议 |
| 科技前沿 | 半导体计算、机器人、量子、航天、生物科技、能源材料、网络安全 | 重大技术进展优先，普通消费产品小更新默认不收录 |
| 社交话语观察 | 已报道事件的主要论点与分歧、平台原生新兴话题 | 披露样本范围，不声称代表总体民意 |
| GitHub 热门项目 | 关注度动量、新项目与已有项目的重大新进展 | Observer 自定义热度，历史降权，不代表官方 Trending 或质量评分 |

每栏目标约 7 条，包括约 3 条 Priority Story 和 4 条 Watch Item；不以低价值内容凑数，不限制整期阅读时长。简体中文为成稿语言，允许多语言发现和核验；常规关注中国、美国、欧盟，其他地区按全球或重大区域影响纳入。

每天北京时间 07:30 截稿，08:30 前私有服务端报告可读。Report Record 保存机器事实和审计，Canonical Markdown 保存唯一发布正文；PDF 从 Markdown 转换，邮件呈现也由同版本内容派生。邮件提供 Today Overview、私有链接，并在附件预算允许时附 PDF。

V1 交付服务端、邮件、MD/PDF 归档下载与稳定同步 API。Phase 2 才实现 Android 客户端，通过主动打开/刷新同步，覆盖无 GMS 手机，不需要推送通知。

## User Stories

以下编号为 PRD 内稳定追踪标识。未标 Phase 2 的故事属于 V1，包括为后续客户端提供的服务端能力。

### 阅读与选题

1. 作为 Owner，我希望每天自动获得 Daily Brief，以便持续掌握重要变化。
2. 作为 Owner，我希望按六个 Edition 阅读，以便快速找到各领域信息。
3. 作为 Owner，我希望看到 Today Overview 中每栏最重要的故事与缺口，以便决定先读哪里。
4. 作为 Owner，我希望每栏约有 7 条且其中 3 条重点，以便兼顾深度与覆盖。
5. 作为 Owner，我希望低质量或无可靠来源时少收录，以便避免被凑数内容干扰。
6. 作为 Owner，我希望整期没有阅读时长限制，以便按兴趣深入阅读。
7. 作为 Owner，我希望正文使用简体中文并保留必要外文名称，以便理解内容并检索原资料。
8. 作为 Owner，我希望检索多语言来源并披露地域覆盖缺口，以便知道全球覆盖的实际边界。
9. 作为 Owner，我希望重点故事解释事件、重要性、影响路径及未知，以便理解信息的意义。
10. 作为 Owner，我希望事实、发布者声明和 Editorial Analysis 分开，以便判断结论的依据。
11. 作为 Owner，我希望同一 Event Cluster 只在主 Edition 完整展开，以便减少重复阅读。
12. 作为 Owner，我希望其他 Edition 用 Impact Note 指向同一事件，以便理解跨领域影响。
13. 作为 Owner，我希望旧事件只有出现 Material Story Update 才重新报道，以便每日内容有新增价值。
14. 作为 Owner，我希望晚发现的重大旧闻标为补报，以便不把旧事件误认为刚发生。

### 来源、可信度与主题特殊规则

15. 作为 Owner，我希望每条重要陈述都能追溯到具体 Evidence，以便核验事实。
16. 作为 Owner，我希望每条故事就近显示来源标题、时间和直接链接，以便访问原始资料。
17. 作为 Owner，我希望看到一手、独立媒体、预印本、社交样本等标签，以便理解证据性质。
18. 作为 Owner，我希望来源冲突或不足时明确标为待确认，以便避免误把争议当作定论。
19. 作为 Owner，我希望战争、伤亡、选举等高风险报道采用更严格核验，以便降低重大误报。
20. 作为 Owner，我希望动态数字附统计时间且单方说法准确归因，以便理解变化和立场。
21. 作为 Owner，我希望财经内容提供事实与影响解释而不发出买卖指令，以便把资讯与投资决策分开。
22. 作为 Owner，我希望 AI 与科技内容区分预印本、官方发布和独立验证，以便辨别证据成熟度。
23. 作为 Owner，我希望社交话语观察同时覆盖故事关联讨论和平台原生话题，以便发现分歧与新信号。
24. 作为 Owner，我希望社交栏目披露平台、查询、语言、时间和样本量，以便判断观察范围。
25. 作为 Owner，我希望没有合规社交样本时显示 Coverage Gap，以便理解缺栏原因。
26. 作为 Owner，我希望所有内容按来源允许的存储、模型处理和分发范围使用，以便持续运行服务。
27. 作为 Owner，我希望只通过配置启用新来源，以便控制 Source Registry 的质量。
28. 作为 Owner，我希望 Research Agent 将新来源作为 Source Proposal 提交，以便发现有价值的扩展来源。

### GitHub 项目发现

29. 作为 Owner，我希望看到 Observer GitHub Heat 的计算依据，以便理解项目入榜理由。
30. 作为 Owner，我希望新项目和成熟项目的新动量都有机会出现，以便避免累计 stars 主导榜单。
31. 作为 Owner，我希望按语言与仓库年龄背景比较热度，以便降低不同生态规模带来的偏差。
32. 作为 Owner，我希望看到真实时间戳支持的 24h star/fork 净变化，以便区分动量与累计规模。
33. 作为 Owner，我希望新采集项目明确标注 Cold-start Heat，以便不把代理热度当实测增长。
34. 作为 Owner，我希望 Previously Covered Project 自动降权并逐步恢复，以便减少重复且不永久错过项目。
35. 作为 Owner，我希望项目改名或转移后仍保留报道历史，以便避免重复入榜。
36. 作为 Owner，我希望重大 Release、安全事件或再次爆发可以一次性重新入榜，以便跟进重要变化。
37. 作为 Owner，我希望安全事件明确标为风险更新，以便不把安全问题误解为安装推荐。
38. 作为 Owner，我希望快照、查询或排名数据不完整时明确降级，以便不把样本排名当全局完整榜。
39. 作为 Owner，我希望候选代码与二进制不被自动执行，以便项目研究不会直接影响服务主机。
40. 作为 Owner，我希望已发布排名能用保存的证据重算，以便追查排序与增长数字。

### 定时、恢复与更正

41. 作为 Owner，我希望每天 07:30 冻结材料并于 08:30 前服务端可读，以便形成稳定阅读习惯。
42. 作为 Owner，我希望截稿后普通新消息留到下一期，以便当期有明确时间边界。
43. 作为 Owner，我希望截稿后发现重大错误仍能修正，以便时间边界不会阻止纠错。
44. 作为 Owner，我希望单个 Edition 失败不拖垮其他栏目，以便仍能获得当日有效信息。
45. 作为 Owner，我希望 Degraded Brief 清楚说明缺失内容和原因，以便理解报告可靠性。
46. 作为 Owner，我希望 Agent 都不可用时仍能收到许可允许的来源链接，以便保持基本信息可达。
47. 作为 Owner，我希望节点恢复后在当日恢复窗口内补跑，以便获得明确标记的 Delayed Brief。
48. 作为 Owner，我希望超过恢复窗口时记录 Missed Brief，以便不把事后产物伪装为准时报。
49. 作为 Owner，我希望已发布日报的缺栏在 12:00 前恢复后产生 Completion Revision，以便补齐内容并保留历史。
50. 作为 Owner，我希望每天复查最近 7 天报道的更正与撤回，以便持续修复已发布错误。
51. 作为 Owner，我希望可靠更正生成新 Report Version、重大未解错误先撤回，以便知道哪些旧结论失效。
52. 作为 Owner，我希望重大事实更正再次发邮件，以便无需主动重读历史也能获知变化。
53. 作为 Owner，我希望重试与重启不会重复发布或重复触发已完成的投递，以便避免重复日报。

### 呈现、归档与访问

54. 作为 Owner，我希望 MD、PDF 与邮件来自同一版本内容，以便跨渠道阅读不发生事实漂移。

59. 作为 Owner，我希望归档显示更正、取代和撤回关系，以便避免继续依赖旧版本。
60. 作为 Owner，我希望报告和同步接口默认鉴权，以便保持个人内容私有。
61. 作为 Owner，我希望设备能通过一次性配对建立可撤销访问，以便管理客户端权限。
62. 作为 Owner，我希望在无 GMS 的 Android 手机主动打开后同步，以便无需通知体系也能读日报。（Phase 2）
63. 作为 Owner，我希望客户端按日期/Edition 浏览并查看更正和重新下载，以便在手机管理历史阅读。（Phase 2）

### 配置、运行与验收

## Implementation Decisions

本节记录已确认的架构与产品契约，不指定尚未选择的编程语言、数据库、运行参数或供应商。模块是逻辑责任边界，不意味着拆成独立微服务。

### D1. 版本与范围

V1 实现六个 Edition 的私人服务端、来源/兴趣配置、日报生成归档、邮件、MD/PDF 和客户端同步契约。Android UI 与实际设备体验在 Phase 2；没有公众账户体系、配置网页或人工编辑器。日常自动生产与上线前人工验收分开。

六个栏目使用共同出版规则。Priority Story 软目标 400–800 中文字，复杂条目最多约 1200 字；Watch Item 约 100–250 字。原始正文和短引文使用受 Source Policy 限制，不因字数目标扩大复制范围。

### D2. 逻辑模块与主要契约

| 逻辑模块 | 输入与输出 | 责任 |
|---|---|---|
| 来源与兴趣配置 | 已审阅 Source Policy、Interest Profile → 生效配置版本 | 管理允许来源、偏好、排除与 Global Baseline |
| Collector 与 Evidence 管理 | 来源响应 → 规范化 Evidence、缺口、截止快照 | 持续采集，执行来源限制，记录时间与出处 |
| Story Selection | Candidate Story、历史与偏好 → Event Cluster、主栏目与选题 | 去重、新进展、补报、排序和跨栏关联 |
| AgentRunner | 限定材料、编辑任务与输出约束 → 结果、运行终态与消耗 | 封装 Codex/Claude 调用与生命周期 |
| Edition Research 与 Publication Gate | Evidence、Agent 结果 → 可发布故事或隔离/待确认项 | 核验内容，分开结构有效与事实有效 |
| Final Editor 与 Rendition | 已校验 Report Record → Canonical Markdown → 派生产物 | 跨栏统一、总览与内容一致性；不能新增事实 |
| 出版归档与交付 | 通过门槛的版本 → 私有归档、下载/同步、投递状态 | 原子发布、版本关系、去重、邮件与访问权限 |
| 调度、巡检与恢复 | 业务时钟、任务状态、备份 → 补跑、纠错与恢复记录 | 独立失败恢复、有限重试、备份及可观测性 |

遵循 ADR-0001：确定性采集与发布流程包围可替换 Research Agent，Agent 不是唯一新闻源，也不是最终发布权限持有者。

### D3. 信息对象与时间语义

- Source Registry/Source Policy：来源身份、出处、审阅状态、允许字段、模型处理范围、缓存期限、引用与分发限制、删除规则。
- Evidence：来源标识和直达 URL、事件时间（可未知）、原始发布时间、首次发现/获取时间、来源类型、允许保存的证据与哈希。未知时间不能由 Agent 捏造。
- Candidate Story/Event Cluster：同一事件与独立进展的关联、主 Edition、跨栏 Impact Note、补报标记、重要性判断及证据关联。
- Report Record：业务日期、覆盖窗口、配置与运行版本、选题、分析、陈述到 evidence_id 的关系、来源政策决定、缺口及生成元数据。
- Report Version：稳定刊次标识、版本、发布实际时间、修订原因、前后版本关系及各 Rendition 标识；不可静默覆盖。
- Repository Snapshot：稳定 repository node ID、观测时间、累计 stars/forks、数据完整性、评分需要的允许元数据。
- 运行与投递记录：任务关联、Provider/模型/CLI 版本、状态、重试、终态、用量以及服务商消息标识；秘密不得进入记录正文。

全部持久化时间采用 UTC；业务时区显式为 Asia/Shanghai。按本期首次披露或实质新进展选择新闻；事件发生早不自动排除今日首次披露。漏采旧闻仍有重大价值时标明 Late-discovered Story；无新进展不重复。

### D4. 截稿、发布与恢复

07:30 冻结正常选题 Evidence Bundle。生成阶段补充核验受 Source Policy 约束；截稿后新证据只用于更正当期重大错误，不加入普通新故事。补充证据保留进入时间及用途，不能反向伪造截止快照。

08:30 以服务端私有 Report Version 可读为硬交付点，邮件受理和投递独立记录。各栏目独立失败重试；系统可发布完整、内容降级、延迟或同时延迟且降级的报告。

| 触发 | 对外行为 |
|---|---|
| 正常完成 | 在截止目标内发布可读版本并触发邮件交付 |
| 部分栏目失败 | 发布有效部分并明确 Coverage Gap，不凑数 |
| Agent 均不可用、采集仍有效 | 仅呈现策略允许的标题、来源、时间和链接；禁止伪造摘要分析 |
| 整期无可信内容 | 记录失败；在恢复窗口内继续有界恢复 |
| 整期当日 12:00 前恢复完成 | 发布 Delayed Brief，写明真实时间 |
| 从未发布且超过恢复窗口 | 记录 Missed Brief，不事后伪装准时报 |
| 已发布缺栏在 12:00 前恢复 | 产生 Completion Revision，材料仍属于原刊窗口 |
| 已发布缺栏在 12:00 后恢复 | 不再补刊，保留缺口；新进展按下期规则处理 |
| 出现可靠事实更正 | 重新核验后发新版本，重大事实更正再次发邮件 |
| 已发布条目存在无法解决的重大错误 | 先撤回相关内容并说明状态，不等待补刊窗口 |

12:00 限制恢复首发和补齐，不限制纠错/撤回。是否缺刊、是否降级、是否迟到、版本是否被取代/撤回、邮件是否送达分别表示，不合并成含混的单一“成功”状态。

同一期重试和重启不得导致重复版本或重复已完成投递；超时不代表外部邮件服务未受理，具体幂等/对账策略应由邮件适配器契约说明。

### D5. 证据、选题与更正

普通事实要求一个适当 Primary 来源或两个独立可靠来源；同一上游稿件的转载不能算两个独立来源。官方声明仅证明声明本身，不能自动升级成独立验证。高风险世界要闻至少两个独立可靠来源；高风险财经采取更严格交叉核验。

来源类型和研究状态标签可组合，预印本标明未必同行评审。状态使用可解释等级，拒绝未经校准的精确可信度概率。来源冲突展示归因、区间与未知；单方说法明确归因，伤亡/计票等数字带时间；不使用未核验社交视频或血腥图片。

Editorial Analysis 可以阐释影响路径和竞争解释，不能包装为事实。直接引语核对原文、译文明确标识。每个重要陈述关联具体证据；JSON Schema 通过只能证明结构有效，事实支持仍需核验。

每次日更生成前复查最近 7 天报道的来源更正、撤回和重大冲突。Correction 新建版本并关联受影响内容；普通新进展进入下一期，不能作为修改旧刊的理由。无人工编辑器或人工 override，来源配置维护仍由 Owner 负责。

### D6. 来源与偏好

Agent 可以提出 Source Proposal；Owner 通过配置启用后才加入可用 Source Registry。已批准来源上的日常任务不需要人工审批。未知来源可以发现事件，不能单独成为发布依据。

来源策略在采集、存储、进入模型和分发阶段执行，不以 Prompt 自律代替。默认只发布原创短摘要、必要短引文、允许元数据及直达链接；不复制全文、图片或付费墙内容。财经优先监管与统计一手源，FRED 和未获许可行情保持默认排除，直到用途获得重新核查和批准。

社交观察分为 Story-linked Discourse 与 Platform-native Signal，必须显示平台、查询、时间、语言、地域依据、样本量和缺口。X/Reddit 等未经明确许可的数据不进入 Agent 与不可撤回导出物。样本不足显示缺口，不推出总体支持率或个体画像。

Interest Profile 为显式可版本化配置，包含主题、实体、地区、优先级、排除项。Global Baseline 维持重大事件入选资格。不采集阅读时长、不隐式学习、不静默更新偏好。

### D7. Agent 运行

V1 统一封装 `codex exec` 与 `claude -p`，以受控子进程执行，输入材料、工作目录、权限、输出 Schema 和时限显式给定。检查进程退出、结构结果与运行终态，不能把部分文本当成功。后续可以在相同业务契约下切换 SDK。

六个 Edition Research Agent 分工，一次任务选一个主 Provider；另一 Provider 承担条件复核、降级或影子对照。Final Editor 统一跨栏内容和总览，仅访问已校验 Report Record，不联网、不运行 shell、不引入新事实。分工数量不承诺并发数量。

Research Agent 只读材料和受控检索/MCP；禁止执行候选代码、下载二进制、改配置或外发邮件。网页内容属于不可信材料，不能更改任务规则或读取秘密。工具权限、命令出网、内建检索和 MCP 等通道分别控制。

V1 不设业务预算上限，但每次运行记录消耗，并对总时长、调用轮数、重试、并发和异常增长设置有界控制。具体值经容量测试确定，不沿用研究示例中的临时金额。

### D8. GitHub 热度

遵循 ADR-0003，Observer GitHub Heat 是关注度动量与新颖性，不复制官方 Trending。官方 API 搜索/仓库/Release/安全元数据构成发现与观测材料，不假定覆盖全 GitHub。

- 仓库主键采用稳定 node ID，改名转移保留历史；不限制编程语言，主题按兴趣加权，使用语言/年龄 cohort 比较。
- 排除非公开、不可访问、archived、disabled、fork、mirror、template 仓库。无法判断的风险项隔离；不声称隔离必然证明恶意。
- 每小时观测累计 stars/forks；24h 净增是两个快照差，负数原样保留。当前快照容忍 ±15 分钟，历史快照容忍 ±60 分钟，并展示真实观测时间。
- 07:30 冻结的因果约束优先于快照容忍范围：当期计算不偷用截稿后普通新观测。快照调度相位需要在规格中满足截止与容忍要求。
- 历史不足时独立标识 Cold-start Heat；其他缺样、搜索不完整、限额失败显式降级，不能混作可信 24h 正式排名。
- 报道后 7 天普通冷却，之后在 30 天内线性恢复，再受近 90 天报道频率惩罚；不永久排除。
- 每期至少一半位置面向过去 30 天未报道项目，质量不足则减少数量，不为配额纳入低质量项目。
- 重大稳定 Release、明确关联的高危/严重安全事件、极端再次增长可以触发一次性 Re-promotion Event；按事件身份/实质修订去重，展示原因。普通更新不能重复绕过，安全事件呈现风险更新。
- 保留评分版本、使用的样本与降权/升权理由。小时快照 90 天后压缩为每日快照，但已发布数字所需的计算证据继续保留；报道历史和事件去重标识长期保存。
- V1 使用有到期时间的最小只读 fine-grained PAT，秘密只在服务端保管。

最终权重、极端分位、cohort 小样本处理及配额/事件冲突的精确优先级未在讨论中选定，需回放验证后写入技术规格。研究示例公式不是已批准的实现常量。

### D9. 正文、文件与同步契约

Report Record 是事实审计底稿；Canonical Markdown 是唯一发布正文。PDF、邮件 HTML 和未来客户端阅读内容来自同一 Report Version；邮件总览可以是正文子集，不要求与全文字数相同，也不能自行新增内容。

PDF 需保证中文、标题、列表、分页和链接可读。邮件采用固定 HTML 模板、Today Overview 与短期私有链接；附件预算允许时附 PDF，否则提供下载。按 [Owner 最新选择](planning/v1/OWNER-INPUTS.md#邮件)，使用可替换传输适配器，首个实现为 QQ SMTP/TLS + 授权码。同版本邮件对象链接有效24小时且沿用当前身份撤销检查，普通鉴权下载签名仍为5分钟；具体附件预算与未知受理处置见 [#19 实施说明](implementation/v1-19.md)。

V1 提供私有历史列表、按日期/Edition/版本读取、MD/PDF 获取、当前版本及撤回/取代关系查询，并提供同步变更所需的稳定契约；精确路由、分页、游标与认证寿命在技术规格中定义，不虚构现有 API。

未来设备通过一次性配对建立可撤销凭证。Android 在 Phase 2 主动打开/刷新时鉴权同步，显示缺刊、降级、延迟和新版本，不依赖 GMS、通知或后台定时成功。客户端全文搜索后置，离线容量与具体 UI 尚未指定。

### D10. 部署、归档与恢复

2026-09-08 Owner 更新，遵循 ADR-0006：首轮使用本机已登录 Codex 的 native 入口，并跳过项目国家/地区审查，不再以地区输入阻塞。CLI 自行使用已有认证，不复制凭据、不伪造容器/API 执行证明。未来仍可采用云厂商中立、私人控制的单节点 Linux VPS；VPN 用于安全管理，腾讯云与 COS 是候选而非必须采购。实际服务拒绝如实记录，不作为新增网络规避权限。

接受单节点故障，无自动接管或高可用承诺。应用容器化，持久状态与秘密分离，HTTPS 与鉴权保护公网服务。配置、数据库一致性备份、报告索引和成品存入节点外私有对象存储，发布后及时备份成品。

RPO ≤24h、RTO ≤4h 为验收目标，需实际恢复演练证明；每季度至少演练一次。长期保留 Report Record、MD/PDF 与允许的证据元数据/哈希；原文按来源策略保留，社交删除规则优先，脱敏 Agent 事件日志保存 30 天。密钥不得进入普通备份、报告或 Prompt 归档。

## Testing Decisions

### T1. 主要测试边界（已确认）

当前工作区没有产品代码、现成测试或可复用测试边界，因此不声称已有测试先例。提出一个主要业务集成边界：从“业务日期、时钟、来源输入、配置、历史状态与 Agent 结果”触发整期生产，观察最终 Report Version、正文与派生产物、缺口/更正关系、归档可读性和投递结果。

在这个边界注入可控时钟、来源响应、AgentRunner 和交付替身，从外部业务结果判断正确性。不要断言内部私有方法调用次数、类结构或提示词逐字内容；输入相同的固定证据不要求真实模型逐字生成一致文本。

少量边界契约测试验证真实 CLI 事件/退出与结构输出解析、来源 API 分页/限额、邮件受理/未知投递状态、对象存储及鉴权行为。真实模型的事实质量另用影子评测验证，不能由替身集成测试替代。

| 编号 | 场景 | 必须观察到的结果 | 故事关联 |

### T3. 影子评测与生产准入（已确认）

连续 14 天使用相同 Evidence Bundle 比较可用 Provider，结果只进入测试归档。人工核查全部 Priority Story 及至少 20% Watch Item，并记录事实支持、错误归因、漏报、重复、分类、中文表达、失败率、耗时与成本。

| 指标 | 通过要求 |
|---|---|
| 伪造来源 | 0 |
| 严重事实错误 | 0 |
| 抽查事实有证据支持 | ≥98% |
| 发布候选结构与来源政策 | 全部通过 |
| 服务端准时可读 | 14 天中至少 13 天在 08:30 前 |

以上是目标，尚未执行评测。样本中的事实支持比例以核查的事实陈述为分母，不以链接是否可打开代替。严重错误判定例子、抽样记录与计数细则须在评测前固定，避免事后调整口径。

仅一个 Provider 可用时可以验收其能力，不声称双 Provider 对照/切换通过。两者均不可用时，链接降级版仅证明采集和交付，不证明 Agent 内容质量。季度恢复演练、PDF 视觉检查、邮件实际投递和 Phase 2 真机验收都有独立证据，不能用自动结构检查代替。

## Out of Scope

- 多用户、多租户、公众注册、付费运营、公开新闻门户和应用商店公开分发。
- 实时新闻警报、盘中行情、个性化交易建议、目标价、持仓与私人邮件/聊天数据接入。
- 日常人工编辑器、人工内容 override、网页兴趣配置后台、隐式阅读行为学习。
- 强制完整全球召回、强制凑满栏目条数、固定整期阅读时长。
- 镜像新闻全文/图片、README/源码、官方 GitHub Trending 页面，或执行候选项目。
- V1 Android 客户端 UI、FCM/厂商推送、后台及时通知、全文搜索。
- Kubernetes、多节点高可用、自动故障转移，以及通过 VPN 改变供应商出口身份。
- 本次文档工作不包含开发、资源购买、部署、付费 Agent 调用、14 天评测执行或真实投递。

# V1-19：同版本邮件交付与未知受理对账

已接入 `main → production-runtime → Observer → publication outbox → email_notifications → email_deliveries → 可替换传输 → 私有状态 API`。默认禁用邮件。本票没有读取真实邮箱地址、`QQ_SMTP_KEY`、Owner 本地输入或 HOME 凭据，没有 SMTP 连接/预检/发送、真实 Provider/来源调用、Docker 或部署。已有一次 QQ 自测和 Owner 中文收件确认是历史预检，不能代表本实现已通过真实邮件验收。

## 运行配置

使用已有 Node 24.18+ 的24.x，`npm ci` / `npm run build` 后从原 `OBSERVER_RUNTIME_CONFIG` 启动。配置默认 `"email": { "enabled": false }`；明确配置下面字段才启用，示例全部为占位内容：

```json
{
  "email": {
    "enabled": true,
    "transport": "qq-smtp",
    "address": "observer-example@qq.com",
    "publicBaseUrl": "https://observer.example",
    "startBusinessDate": "2026-09-09"
  }
}
```

`address` 同时用于 SMTP 登录、From 和 To，支持 QQ/foxmail 的单个 ASCII 邮箱，符合 Owner 的同邮箱选择。实际地址只放受控本地运行配置，不提交公共仓库。`publicBaseUrl` 必须为无账户信息、路径、查询参数或 fragment 的 HTTPS origin；部署者负责让它指向已有私有 API。服务仍只监听127.0.0.1，公网 HTTPS 代理属于 #23，本票不声称示例域名可访问。

授权码仅通过进程环境 `QQ_SMTP_KEY` 懒注入。先验证完整启用配置和 MIME 预算，真正发送时才读该变量；构造适配器不连接或预检，禁用邮件不读变量。缺少/格式无效授权码形成 `rejected / smtp-auth-failed`，停止自动尝试；不要把授权码写入 JSON、日志或命令行。

`startBusinessDate` 是邮件通知最早刊次，避免启用时无意发送整个归档。符合日期的既有 pending outbox 可消费；升级不为从未存在 outbox 的旧手工报告虚构发送历史。通知首次进入处理器时冻结发件人、收件人、传输及传输来源，后续修改邮箱不会自动把已排队/完成通知转寄或复制给新地址；不匹配当前传输配置的旧 pending 项保留待本地处理。关闭邮件会保留全部持久通知，恢复相同配置后继续安全待办。

邮件处理器每秒独立运行，不依赖 `schedule.enabled`、采集或当天研究完成；进程内至多一项邮件工作，SQLite claim 防止多个本地进程同时发送同一项。PDF 处理器同样独立，既有 MD 的发布及08:30首次可读指标均不等待邮件。

## 同版本内容、预算与私有链接

只通过现有 `readReport()` 取得完整、持久的 Canonical Markdown，在 `## Today Overview` 与下一栏目/二级标题之间截取原文。固定 HTML 模板保留该子集及版本/修订身份，不接受 `record.stories` 作为邮件事实输入；Completion 中“本次补齐”“保留前版本内容”与覆盖缺口均来自该版原文。旧报告无总览时标为 `blocked / email-overview-unavailable`，不重新研究或猜测。

CommonMark 渲染禁用原始 HTML 执行、linkify 和自动改字；源 HTML 转义为可见文字，图片仅保留替代文字，不读取网络或文件。总览链接保留文字标签；固定、受校验的本版本下载链接是 HTML 中唯一可点击 URL。MIME 的文件/URL读取均禁用，PDF 只用已校验 Buffer；无模板执行、附件路径或远程资源输入。

| 技术决策 | 行为 |
|---|---|
| 等待 PDF | 从通知进入交付队列起最多120秒；pending/processing 每秒重新检查，failed/无产物立即回退 |
| 原始附件预算 | PDF ≤5 MiB |
| 完整邮件预算 | 实际 MIME Buffer ≤8 MiB，包含头、HTML、纯文本和编码后附件；这两个数是项目预算，不是 QQ 上限或受理承诺 |
| PDF 就绪 | 复用同版本 `pdf.read(report)` 授权与产物来源检查；预算内附 PDF，超预算仍给同版本 PDF 下载链接 |
| PDF 尚不可用 | 提供同版本完整 Markdown 的可用下载授权，明确未附 PDF 原因；不等待未来 PDF、不借用旧版本附件 |
| MIME 超预算 | 有附件时移除附件重新生成同版模板；仅总览仍超过预算则明确 blocked，不截断事实 |
| 邮件对象链接 | 固定版本、格式、Owner 身份和用途，有效24小时；邮件中明示UTC到期时刻 |

实际发送使用已经测得长度的同一编码 Buffer；SMTP 适配器不会再次生成 MIME。发送前、异步 MIME 准备后、签发下载前均沿用现有版本撤回和当前 Source Policy 检查。PDF 已存在但不满足来源/完整性条件会阻止发送，不绕过授权。已发送的附件无法远程擦除。

邮件用途签名只由本地受控交付路径签发；无新公开签发路由。普通 Owner/设备 `POST .../download-link` 仍是5分钟。邮件点击现有 `GET /v1/downloads/<version>/<format>?token=...` 无需 Bearer，访问时重新检查当前 Owner 密钥、报告撤回和来源权限；替换 Owner 密钥后旧链接失效。URL没有长期 Owner/设备 Bearer。

签名 URL 只存在生成邮件的内存中，不存入交付状态、事件、日志或报告；状态仅记录格式和到期时刻。代理访问日志必须屏蔽下载查询串。过期后的精确归档地址需要 Bearer，只是受权程序客户端重新获取的入口；V1没有浏览器登录或 Android UI，不承诺普通浏览器点击该回退地址可读。

## 事务与状态

报告 INSERT 的 SQLite trigger 为 initial/completion 写入原 `delivery_outbox`，与报告及既有调度提交同事务；原调度发布使用幂等 INSERT。Outbox INSERT 再同事务写 `email_notifications`，启动时导入已有 outbox。处理器将通知和冻结收件人转为唯一 `email_deliveries`，提交后才消费。交付身份由刊次、版本、收件人、通知类型共同唯一；另以 notification ID 防止修改收件人后自动复制同一通知。

状态为 `pending → preparing → sending → accepted | rejected | unknown`。只有明确未受理的暂时错误可回 pending，间隔5分钟，最多3次实际传输尝试，耗尽为 failed。授权/正文问题为 blocked；发送准备不计入 SMTP 次数。accepted、rejected、unknown、failed、blocked 都不自动重发。SMTP内部不做发送重试，Message-ID 只作本地追踪，不是 QQ 幂等键。

发送调用之前先持久化 `sending`、尝试号、本地 Message-ID 和 `attemptStartedAtUtc`。该时间只表示开始调用适配器，**不是** SMTP DATA 已提交或受理的证据。22分钟租约过期时，preparing 可以回 pending；sending 则保留 unknown，不依据 PID、超时或断连猜测没有发送。收到最终250之后、落库之前崩溃也走 unknown。优雅退出中止在途 SMTP；无法确认的发送保留 unknown。

| 状态 | 含义 |
|---|---|
| publication | 报告版本真实发布时间与当前取代/撤回状态，与邮件分开 |
| accepted | 观察到该收件人的最终 SMTP DATA 250；`acceptedAtUtc` 是本地观察时刻，不表示已进收件箱 |
| delivered | 仅由本地记录的实际 Owner 收件确认或服务商投递证据推进 |
| bounced | 仅由实际服务商退信证据推进 |
| rejected | 明确拒绝或本地配置拒绝；看 reason 区分，SMTP responseCode 只保存确有的数字 |
| unknown | 提交结果或崩溃恢复无法确认，无 QQ 查询/幂等/回调契约时保持待查，不盲重发 |

私有 `GET /v1/reports/YYYY-MM-DD-vN/email` 复用 Owner/设备 Bearer。返回 publication、enabled、通知及每项交付的状态、尝试、真实可得的时间/标识、脱敏原因、MIME大小、附件/格式/到期信息、状态历史及本地对账引用。已撤回报告仍可读交付元数据；测试报告继续不向生产暴露。收件人显示 `configured-owner`，不返回邮箱、正文、SMTP原始响应、令牌或签名查询串。`messageId` 是本地生成的 RFC Message-ID；QQ没有已核实的响应ID解析契约，因此 `providerMessageId` 保持 null，不把原始响应或本地ID伪装成服务商标识。未取得实际投递/退信时间即保留 null。

## 本地证据对账与 #20 接口

本票没有 QQ 查询、回调或邮箱读取能力，不自动确认投递。操作者掌握实际证据时，可以用已有文件系统权限对运行服务的确切数据库记录：

```sh
npm run email -- --database data/observer.sqlite reconcile data/operator/email-evidence.json
```

本地证据 JSON 字段：`eventId`（新的UUID）、`deliveryId`（状态API的UUID）、`state`（accepted/delivered/bounced/rejected）、`source`（owner-confirmation/provider-evidence）、`evidenceReference`（仅本地短引用标识）、`occurredAtUtc`（已知实际UTC时刻或null）、`providerMessageId`（确有的短标识或null）。不要填入原始邮件、QQ地址、URL、查询串或秘密；引用只允许128字符内的字母/数字/点/横线/下划线/冒号。Owner确认只可说明 delivered。

这条命令是操作者对证据的本地声明，不是经密码学验证的 QQ 回调；不会访问邮箱验证真实性，也不会发送或创建签名。重复相同 eventId/内容幂等，不同内容冲突；旧证据保留审计但不把 delivered 回退到 accepted。unknown 可由实际证据推进，accepted 可推进 delivered/bounced。无证据仍为 unknown；确认拒绝也不会触发重发。证据记录时间与实际发生时间分开，未知时间保留null。没有公开管理/重发路由。

`src/email-delivery.ts` 导出 `enqueueEmailNotification(database, { versionId, kind, atUtc })`；#20可以在自己的发布事务内、报告 INSERT 后调用 `kind: "significant-correction"`，要求该版本 revisionReason 为 correction。日常通知为 daily-brief，只接受 initial/completion。同版本/类型重复幂等。Observer 同名方法供受信本地调用；需要与发布原子提交时必须使用底层同连接函数。正式纠错证据门、重大性决策、更正发现与版本生成属于 #20/#21，本票未实现这些流程。

## QQ 适配器与验证范围

锁定 Nodemailer 10.0.1（MIT-0，自带类型）；使用其 MIME stream composer 与公开 SMTPConnection 导出，便于区分认证前失败和发送后未知，并在截止/取消时关闭该连接。固定 `smtp.qq.com:465`、隐式 TLS、最低TLS1.2、证书和主机名校验开启，禁止端口自动回退。DNS/连接/问候/空闲超时分别30秒/120秒/300秒/600秒；整个事务上限20分钟，租约22分钟。只有显式 SMTP 4xx/5xx负回复能表明未受理；send()开始后任何其他断连/超时保守 unknown。最终250才是 accepted，RCPT250或DATA354都不算。关闭原始协议、正文及事务日志。

# V1-23：单节点 Linux 容器运行

本票交付可部署的软件与操作说明。按 Owner 最新 RAPID V1 授权，仅在完整功能块末做一次类型检查；Linux 容器启动、容量、故障与重启矩阵延期至 #26。没有执行 Docker、真实模型、来源采集、SMTP、证书申请或服务器操作，也没有读取本机 Owner/Provider/QQ 秘密。API、邮件、MD、PDF 是 V1 交付面；没有管理 Web、Android、Kubernetes、HA 或自动接管。节点外备份及恢复编排属于 #24。

## 入口与数据布局

`deploy/Dockerfile` 构建 Node 24.18.x–24.x 应用，包含编译后的 `dist`、生产模块、Python worker 源码、PDF 中文字体及 OFL 许可证、Docker CLI、CA 和 flock。构建上下文由 `.dockerignore` 白名单限定，排除所有 Owner data、数据库、认证、IDE、Git 与测试目录。默认基础镜像版本仅为待构建输入，本票没有拉取或证明这些 tag 可用；正式发布保存确切应用与 Agent 镜像身份、源码提交、配置版本，禁止复用同一 release tag。Agent 既有 sha256 运行身份和内容完整性功能保留，不进行开发验收 hash。

Compose 仅 HTTPS 代理发布宿主 80/443；80 用于 ACME 与 HTTPS 跳转，应用 3000 没有宿主端口映射。应用以显式 `OBSERVER_BIND_HOST=0.0.0.0` 供容器代理访问；原生默认仍是 127.0.0.1，自查私有报告继续走本容器 loopback。API 鉴权、一次性配对、限时下载凭证沿用 #17，代理不承担替代鉴权。`/v1/ops` 仅 Owner token 可访问，而且代理明确拒绝这个路径。

| 宿主布局 | 容器内位置 / 权限 | 用途 |
|---|---|---|
| `/srv/observer/data` | `/var/lib/observer`，app UID/GID 10001 可写 | 报告、Canonical MD、PDF BLOB、任务/路由/交付状态；collection 与可选 GitHub SQLite |
| `/etc/observer/config` | 同路径只读 | `runtime.json`、Owner 已审来源策略、兴趣配置；有邮箱时此目录也属私人配置 |
| `/etc/observer/secrets/owner-token` | `/run/secrets/owner-token`，只读 | Owner 管理凭证；不能从 public 配置取值 |
| `/etc/observer/provider-secrets` | `/run/provider-secrets`，只读 | 可空；仅放实际启用的 API/SMTP 专用秘密 |
| `/srv/observer/tls` | Caddy `/data`，仅 UID/GID 10002 | 自动 HTTPS 证书与私钥，应用和 Agent 均不挂载 |
| 无持久宿主材料 | app `/run/observer`、`/tmp` tmpfs | 健康心跳、Docker CLI 空配置、任务临时目录 |
| 无 app/data/secrets 挂载 | 独立 Agent 的 `/run/observer` tmpfs | 无网络、UID 65534、只读根、无 capabilities、最多 32 PID、1 CPU、Codex 256MiB / Claude 512MiB |

本地 SQLite 文件与其 WAL/SHM 必须位于同一持久本地文件系统，不放 NFS。目录预先创建，Compose `create_host_path:false` 阻止路径笔误悄悄生成空目录。`flock --no-fork` 对同一数据目录持有单应用排他锁，重启后由内核释放；不要启动另一项目/collect 命令同时写这一运行目录。

应用通过宿主 Unix Docker socket 管理 Agent，这是具有宿主 root 等效能力的受信管理面；只读 socket 挂载不限制 Docker API 权限。app 非 root、只读根和网络分组都不能消除这个权限。不要共享宿主给不可信租户，不把 socket、Provider 凭证或应用目录传给 Agent。代理只共享容器网络，不共享 app 数据/秘密。app 和代理具备出站网络；Compose 没有声称实现主机级目的地址防火墙。来源安全读取和模型 parent broker 继续约束实际请求，VPN 仅用于管理，资格条件沿用 ADR-0002。

`agent-container.ts` 把镜像中固定的 worker 代码作为 Python `-c` 参数传入，任务与证据继续是 stdin 数据。它不再把应用容器的 `/app/dist` 路径当作 Docker daemon 宿主文件；正式 Agent 没有代码 bind mount。仅原有 protocol-fixture 保留替身文件挂载，不能据此证明容器内真实运行。worker argv 只有受信程序代码，不含任务、Prompt、账户或秘密。Agent PID 1 自带最多 300 秒截止计时，即使 parent app 消失也会退出，其进程树随容器停止；正常路径仍按已确认不可变容器身份清理。

## 首次安装（仅供获得目标主机授权后执行）

目标是单个 Linux amd64 节点、Docker Engine + Compose v2 与 systemd；现有固定 Codex/Claude 包是 x64，ARM 未资格化。Node 固定到 `>=24.18.0 <25`。建议初始 4 vCPU、8 GiB RAM、40 GiB 本地 SSD，这些是预算起点，未做容量测量。公开 DNS A/AAAA、80/443 入站及证书申请必须对应获授权域名；仅发布管理 SSH 到受限入口。后续另行验证实际模型/新闻 HTTPS、DNS、QQ 465 出站和实际地区资格。

1. 保存本提交为不可变 release，在无秘密的构建环境构建：`docker build -f deploy/Dockerfile --build-arg RELEASE_ID=<release-id> -t observer:<release-id> .`。保留 app 镜像，不移动或删除上一版；Agent 仍使用现有准备流程产生的固定镜像身份。准备流程的产品依赖校验不代表本票已执行 hash 验收。
2. 用 root 把 `deploy/` 的 Compose、Caddyfile、两个脚本安装到 `/usr/local/lib/observer`；脚本模式 0755、其余 0644，目录 root 所有且不可由 app 修改。把三个 systemd unit/timer 安装到 `/etc/systemd/system`。保留 release 对应部署文件副本。
3. 新建 app data 目录并设 `10001:10001`、0700；新建 TLS 目录并设 `10002:10002`、0700；配置与秘密目录设 `root:10001`、0750，文件设 0440。检查父目录遍历权限。仅对这次明确创建的目录设置权限，不递归修改既有数据树。
4. 复制 `deploy/deployment.env.example` 到 `/etc/observer/deployment.env`，填写域名、路径、保留的 app/Caddy 镜像、`stat -c %g /var/run/docker.sock` 对应 group ID。该 env 文件只含路径/非秘密值；`OBSERVER_NODE_ID` 是稳定小写字母数字横线标签，唯一标识本节点。
5. 复制 `deploy/runtime.example.json` 为配置目录的 `runtime.json`，同时放入经 Owner 审查的 `sources.json` 与兴趣 `interest.json`。仓库示例可作为初始输入，但不是来源授权。所有生产功能默认关闭；已存在报告的 PDF 默认启用。来源配置文件缺失必须拒绝启动，不能用空 sources 代替读取失败；权利收回则以明确的权威配置/删除契约表达。
6. 由操作者使用私人秘密管理方式提供足够强的随机 Owner token。所选 Provider 的秘密文件名依次为 `openai-api-key`、`anthropic-api-key`、`github-token`、`qq-smtp-key`；不启用则目录可空。不要把值放进命令参数、env 示例、构建参数或日志。`*_FILE` 一旦配置便是权威输入，读取失败不回退环境中的旧值；禁用 Provider 不读取其文件。未提供可用模型凭证时路由记录 runner unavailable，资格过期/账户或地区不合格不能请求模型。状态中的 `runner-configured` 不代表网络实测或供应商认可。
7. 先运行 `observerctl.sh up`，再 `observerctl.sh status` 检查关闭状态、storage 与 agentRecovery；启用 systemd 服务和 timer 才获得重启后启动与看门狗：`systemctl daemon-reload`，`systemctl enable --now observer.service observer-watchdog.timer`。这一步会联系 Docker/ACME，属于 #26 获授权的实机验证，不在本票执行。

启用日报时更新配置版本、起始业务日、逐 Provider eligibility 的 checked/valid 时间、固定镜像身份及能力开关。QQ 配置沿用 #19 的公开 schema，但实际邮箱仅放私人配置；配置 `publicBaseUrl` 为授权 HTTPS 站点。此方案使用专用 API keys，不会复制本机 Codex 登录文件、个人 OAuth 或订阅凭证。模型凭证在构造 runner 时装入内存，轮换后重启；QQ/GitHub 在使用时读取专用文件。更新 bind 文件后用受控 stop/up 重建挂载，避免宿主原子替换后容器仍引用旧 inode。

## 受控命令与分立状态

`observerctl.sh` 只暴露 up、stop、restart、state、status、logs、devices、pair、revoke、retention-status、agents 和精确 agent-remove。管理者必须已拥有本节点 Docker/文件系统权限。pair 只在操作者终端显示一次性代码，不传给日志采集。`logs` 最多读 app 100 行；app 错误仅固定分类，不输出错误对象/Prompt/协议正文。Caddy 默认日志丢弃，避免下载查询凭证或 Authorization 被代理错误日志复制；证书排障需另行受控诊断，不能开启原始请求日志。

`status` 在 app 容器内读取 Owner 文件并访问 loopback `/v1/ops`，不会构造第二个运行时、读取正文、启动任务、检查模型连通性或发送邮件。输出包含进程启动/心跳、磁盘字节/ inode、后台任务进行/失败计数、app 内全局 Agent 并发及 cleanupUnverified、配置开关/限额、Provider 资格与凭证装载分类、采集失败组件与 coverage gaps、当日冻结/研究/可读状态、PDF/邮件/纠错状态计数。

当日细节仍用 `/v1/briefs/YYYY-MM-DD`；同版报告用 `/v1/reports/<version>`，MD/PDF、`/email` 及 archive/sync 沿用现有鉴权接口。`completedAtUtc` 与 `latestReadableAtUtc` 分开；on-time 依据 08:30 前私有报告可读。PDF ready 与报告正文可读分开；邮件 accepted、delivered、unknown、rejected、bounced 各自保留，accepted 绝不等于 Owner 收件可读。缺刊以 missed、补齐以 recovery/content/timing 表达，研究失败和来源 coverage gaps 不能被进程 healthy 掩盖。后台计数只覆盖当前 app 生命周期，持久任务/报告/邮件状态才是重启后权威。

邮件实际证据对账、来源权利删除/恢复契约仍调用 #19/#22 的专用本地 CLI（例如容器内 `node dist/email-admin.js --database /var/lib/observer/observer.sqlite reconcile <已挂载的私人证据文件>`），不增加公开管理写接口或重发命令。文件须由操作者事先放到明确的私人挂载目录，不使用任意宿主根挂载。

## 初始 07:30–08:30 预算（推导，未测）

07:30 截稿冻结与 08:30 私有可读目标仍由 Asia/Shanghai 业务窗口决定，持久时间为 UTC；不依赖宿主 cron/默认时区。正常采集在截稿前完成，07:20–07:30 社交冻结前窗口沿用 #15。纠错巡查默认 06:00–07:15，避免与日报研究争抢主要窗口。

初始路由单 attempt 60 秒、单轮总时限 900 秒、并发进程/外部请求各 2、每 attempt 最多 4 次模型请求、最多 336 次外部请求，research/verification/review attempt 分别 24/30/30，同 Provider 立即重试 0 次。全 app Agent 额外上限 2，覆盖日报与纠错的各自路由；忙时拒绝新容器，由已有路由状态记录 unavailable，不无限排队。cleanup 不可确认则封闭本进程后续 Agent 准入，需先处理再重启。routing 原有 token 用量防失控阈值保留且可配置，它不是产品货币成本硬限。

以六版各一次研究、一次验证、一次跨 Provider review 粗算，18 个 attempt × 60 秒 ÷ 2 并发 ≈ 9 分钟；15 分钟总时限给正常块留约 6 分钟编排余量。最坏 84 个 attempt 即使理想并发也约 42 分钟，超过 15 分钟总时限时会提前截止并留下降级/缺口，不能认为全部都会运行。每日一个快速周期最多三次研究轮：3 × 15 分钟 + 两次 1 分钟间隔 ≈ 47 分钟，距 08:30 约 13 分钟用于提交/可读检查及余量。三次上限只约束短周期，后续按 5 分钟恢复间隔至午前窗口关闭；截止后成功应标 delayed，不能为了按时而跳过发布门。

PDF 单次 60 秒、最多 3 次、重试 60 秒，邮件等待 PDF 最多 120 秒后可用同版 MD 链接；SMTP 总事务最多 20 分钟且未知结果不盲目重试。因此 08:30 不承诺邮件 delivered。app 2GiB + 两个最重 Claude Agent 合计 1GiB + 代理 256MiB，另预留内核、Docker、文件缓存与峰值，8GiB 只是待测起点。实际多 claim 验证、SQLite/字体峰值、代理证书/网络延迟、磁盘增长、QQ 附件及单/双 Provider 均未容量化。

## 重启、故障、升级与回滚

- 正常停止先发 SIGTERM，停止准入、取消在途任务、最多 30 秒等待清理；40 秒容器 grace 是外层保险。SQLite 已提交报告/版本/交付状态持久保存；SMTP 发送后失联仍按未知受理处理，不因重启重发。
- Linux 调度 claim 新增 boot ID + PID namespace + 启动 ticks，区分同 PID 的新容器进程；同 data 的 flock 保证只有一个 app。旧版本未带身份的 running claim 保守依赖旧 PID 规则，应在升级前正常停止；不能把旧 PID 碰撞认定为已自动修复。
- 重启后先读取本节点标记的运行 Agent，最多等 330 秒让旧 worker 自行截止，再开放新 Agent 容器。采集、冻结、降级出版、API/PDF/邮件仍独立工作；等待中的模型请求按 unavailable 记录，避免 Docker 故障连带阻止无模型降级。等待期间 `agentRecovery=checking`；daemon 不可用或仍有旧 Agent 则保持模型准入阻断并显示明确原因，恢复 Docker/旧任务后显式 restart。没有遍历杀进程或自动清空旧容器。`agents` 查看精确身份；只有 app 已停、明确 node 标签且已 exited 的完整 64 位 container ID 才能通过 `agent-remove <id> <node>` 删除，命令复核身份且不 force。它仅处理操作者明确选择的退出容器，可重新从保留镜像创建任务，但该容器本身删除不可恢复。
- app 每 10 秒检查所配置数据库目录的剩余容量，默认低于 512MiB 或 1024 inode 停止新增后台任务。它不删除旧数据、不宣称取消已在途写入或保证 full-disk 时所有读取成功；状态/日志显示 low-space 或 storage-unavailable，需操作者扩容或执行有授权的生命周期维护。Docker 自身所在盘须另由主机监控，`df` 同时关注数据盘与 Docker data-root；daemon 磁盘故障会体现为 Agent unavailable/cleanup-unverified。
- heartbeat 写在 tmpfs，健康检查同时确认其 15 秒新鲜度和 loopback HTTP 响应。Docker 健康状态不负责自动重启；独立 systemd timer 每分钟只对仍运行且 unhealthy 的确切 app ID 操作，最多每小时 3 次，并在 journal 留固定原因。低磁盘、资格不合格和网络失败不是 liveness 重启条件。进程崩溃由 Docker on-failure 最多 3 次处理；停止或耗尽后不由 watchdog 私自启动。看门狗依赖同节点 systemd，节点整体卡死或断电没有外部接管。
- 仅维护时段升级：先 stop 等任务退场，记录当前 release/config/Agent 镜像与持久状态；保留当前 data 及秘密，构建并保存新 release 镜像，更换非秘密 env 中 app reference 与对应配置，再 up。固定冻结快照记录 release/Node/Agent 版本，不同版本不能悄悄续跑原研究，可能产生 frozen-runtime-version-unavailable；如当天快照仍需执行，应恢复对应 release。
- 若新程序失败，stop 后把镜像和兼容配置指回保留的上一 release，再 up；SQLite 已提交新报告与邮件状态保持，不恢复旧数据库来消除失败。跨 schema 不兼容时不要让旧代码强行打开新库；改为恢复该 schema 可用的应用版本，或走 #24 的受控恢复。V1-23 新列为兼容追加，但这不等于已动态验证所有历史版本回滚。
- #24 普通备份不能直接把整个数据目录当作无秘密副本：SQLite `private_access_meta.signing_key` 本身是秘密，另有所有环境/文件凭证及 TLS 私钥。节点外恢复必须使用备份之外保留的最新 #22 删除契约，先应用契约再开放读取/任务，失败则保持服务关闭；恢复设备/下载凭证按 #24 重新签发。本票没有备份、密钥导出或恢复脚本。

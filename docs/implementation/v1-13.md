## 1. 最小 Module 与公共 Interface

继续使用既有 `createGitHubObserver` 的 `observeDue()` 收集公开材料，`createObserver({ github }) → produce → authenticated readReport` 发布和读取。事件不会成为一个无人装配的独立采集进程。

拟增加两个实际有外部变化的 Interface：

1. `GitHubObservationReader.repromotionSnapshot?(cutoffUtc)`：由同一个观察 Module 返回完整有限候选的原 `GitHubRankingSnapshot`，以及有界事件观察、重大性收据、动量区间依据。新的组合收据称 `GitHubRepromotionSnapshot` schemaVersion 1。既有 `snapshot`/`rankingSnapshot` 的数据、顺序、上限及规则不变；`authorize` 接受新的严格联合，重核组合中每项真实来源依赖。
2. `GitHubDevelopmentVerifier.assess(input)`：受信程序装配的外部语义判断，输入是已经采集、当前允许模型处理的 Release 说明或安全范围变化，以及先前已经保存的材料投影。返回输入 SHA 绑定的逐项语义判断。它不是 Request 字段、不是来源权限、也不是实际报道历史。与既有 `SemanticVerifier` 一样，判断质量属于外部质量证据，结构通过不等于真实性证明。

观察 Module 新增可选 `developmentConfiguration: () => unknown` 和 `developmentVerifier` 装配项。前者是版本化、非秘密的启用/范围配置，只允许以既有当轮最多 50 个已核仓库作为 Release 采集集合，不接受自报项目热度、报道历史、事件消费或任意 URL。配置缺失时旧观察行为原样；新 Request 9 明示事件能力缺口，普通 Heat 可继续。

公开确定性重算 `rankGitHubRepromotions({ snapshot, interestProfile, coverageHistory, eventHistory, algorithmVersion })`。它不读时钟、网络、SQLite、环境或秘密。原 `rankGitHub`/`observer-github-heat-v1` 继续独立可用，新函数先调用原排名得到完整普通衰减审计，然后计算事件 eligibility、有效分数及最终配额选择。

Schema 增量为 Request 9 → Record 10 / ReportVersion 9 / `observer-canonical-v8`；新规则为 `observer-github-repromotion-v1`。Record 10 保存完整普通排名输入/结果、事件源收据、语义短投影、长期实际事件历史、全部候选的事件判断和最终选择。旧 Request 1–8、Record 1–9、Version 1–8、旧正文路径原字节保留。

## 2. 权限、原文与外部语义判断

现有 `github.allowApiResponseProcessing` 和 `allowRepositorySnapshots` **不授予** Release/GHSA 正文处理权限。拟新增严格的可选 `SourcePolicy.github.events` 能力契约：

```ts
{
  schemaVersion: 1,
  allowReleaseMetadata: boolean,
  allowAdvisoryMetadata: boolean,
  allowReleaseBodyProcessing: boolean,
  allowMaterialityModelProcessing: boolean,
  allowMaterialEvidenceProjection: boolean,
  allowEventIdentityHistory: boolean
}
```

字段不默认 true。未出现该新契约的旧政策摘要和含义保持不变。实际启用必须由 Source Policy 的递增 `version` 和新的审阅依据明确授权；既有 authority 表拒绝同版本编辑/回滚。公共仓库可 GET 与 Observer 获得模型处理/永久短投影权限是不同事实。继续要求原通用 collection/storage/distribution/citation 和 GitHub 永久派生、不可撤回导出、raw-only 删除范围权限。

原始响应受既有每请求字节、UTF-8、时限、逐跳权限守卫。读取/解码原始 body 本身属于处理，不能把“未发给模型”当作未处理。只有当前明确允许 Release body 处理的来源才启用相应含说明响应采集；按允许字段做最小内存投影，不进入 runs、Report、普通 Agent 输入、异常、日志或归档。缺正文处理许可形成 `major-unconfirmed`/能力缺口，不能用原 metadata 许可偷读说明。没有持久 raw body 缓存，因此不存在把原文 TTL 延长为事件永久许可的问题。语义处理完成必须在 `storage.retentionHours` 和本轮总时限内，零留存/过期材料不能送模型。原通用 model/storage/citation 权限逐项重查；传入旧 development 投影时核其原来源和当前使用权，不用新来源许可洗白旧材料。

verifier 输入与输出拟固定以下事实：目标 observation ID、已核 repository node、上游 Release/GHSA ID、明确 source representation、输入摘要、候选短声明、所引用正文摘录，以及已有同仓库 development 投影；输出逐目标包含 supported/insufficient/conflicting/unsafe、major/routine/unknown、影响类别与范围、规范化 development identity、与旧 development 的 same/new-material 关系和证据依据。枚举不携带权限或代码。Module 自己生成最终 event/revision key，不接受评估器任意 UUID。

确定性检查包括：完整输入摘要匹配、逐目标恰一判断、来源/节点/上游身份匹配、短摘录确在输入材料中、摘录总量不超过 `min(500, source.citation.maxCharacters)`、明确维护者声明归因、关系引用确为输入提供的旧 development、新变化具有非空范围与支持依据、unsafe/conflicting/unknown 一律不授予绕过。评估正文可能判断错误；子串检查只证明引用存在，绝不称其证明语义或代码真实变化。

永久保存允许的短证据摘录、规范化重大变化投影与评估器版本/输入输出摘要，不保存完整说明和其他自由评估散文。归档读取对固定投影和原权限收据重算，不重新请求或重新调用 verifier。撤权时停止对应事件继续出版及旧刊读取；历史消费不能因失权而丢失，见第 6 节。

未知 Release 重大性只阻断该 Release 绕过，不把仓库自动说成不安全；未知或冲突安全风险则继续隔离该仓库。事件派生不产生安装建议。

## 3. 有界采集和真实身份

固定 REST `2026-03-10` 与既有 fine-grained PAT 声明，不增加写权限、GraphQL、源码、二进制、PoC 或任意外链读取。复用现有 Adapter 的限流/退避、严格 DNS/路由、过期检查和 120 秒整轮时限，不叠加一个隐形无限事件时限。

拟定首版有限范围（工程资源界限，不代表全 GitHub）：

- 当轮同 node 详情确认后的每个 eligible 仓库，最多 2 页 Releases，页大小 `min(10, source.limits.maxItems)`；记录响应/next/上限和遗漏。只允许该已核 canonical 仓库的 Release 路由。Release 子路由不自动跟随改名重定向；需要下一次已核仓库地址后重新请求，不能把同 origin 任意仓库当作原 node。
- Global advisories 固定 `type=reviewed`、`sort=updated`、`direction=desc`，最多 3 个经 Link 验证的 cursor 页，页大小 `min(30, source.limits.maxItems)`；不动态猜 cursor。固定只采用 global 表示，不同时采 repository 表示，因此不靠两种可独立编辑内容交替生成修订。
- 另外重查当前有限仓库先前发现的 GHSA，最多 50 个唯一 GHSA ID，允许 high 降级/撤回在增量列表外被观察；超过上限明确风险/监测缺口，不声称其余没变。未知历史不能变成空列表。
- 仅使用 `source_code_location` 的精确 `https://github.com/{owner}/{repo}` 或 `repository_advisory_url` 的正式仓库 GHSA 路由作映射线索，并通过既有仓库详情验证落到当轮 stable node。两个线索存在而相互冲突时隔离，不选一个有利映射；仅包名、CVE、references 或修复依赖不建立关联。只在需要时 GET 经路由验证的仓库详情，不访问返回的任意外链。
- 所有映射响应、Release/GHSA 完整接收、语义判断完成与本地可用时间必须不晚于 cutoff。`published_at/updated_at` 不是 availableAt。字段按正式 required/nullable 处理，Release 的 optional `updated_at/immutable/body` 不默认补值，GHSA 使用当前 `cvss_severities`，不依赖旧 `cvss`。
- 正常元数据即使成功，事件列表失败也会留下事件 Coverage Gap；事件当前失败/撤回/未知不复用上次好事件。没有 GHSA 命中只表示当前有限收集未找到，不表示安全。

当前库仍为 application ID `1329746759` / user_version 1；报告库仍 user_version 1。拟在观察库增加一个 `development_runs(slot PRIMARY KEY, payload)` 表保存新的严格版本化不可变 JSON，原 `runs` JSON 不扩字段。只有新能力启用时，同一次观察 slot 的原 run 与 development run 在一个短同步事务提交；不在网络/模型等待期间持锁。已存在 slot 保留先提交结果，重启/并发调用不重写它。一个 slot 只有旧 run 时，不补写新事件或沿用旧 availableAt，组合 snapshot 明示 `missing-event-run`，下一轮实际补采；启用/未启用并发也以首提交事实为准。

## 4. 事件与实质修订

事件对象身份、观察内容摘要、实质发展身份分别保存。所有 key 排序与大小写处理有固定规则，不把仓库重命名、数组重排、标题/空白、抓取时间、上游 updated 或编排 task ID 放入实质身份。

### Release

stable 必须为 `draft=false && prerelease=false && published_at != null && published_at<=cutoff`。重大性须由上述有支持依据的维护者声明评估完成；不通过 tag、stable、latest、immutable 或出现 major 单词自动认定。

上游 event key 为已核 repository node + Release numeric ID，并保存 Release node ID 的交叉证据。development key 由规范化变化类别/对象/范围产生，复用评估为 same 的既有 key。一次可消耗的 revision key 同时绑定 event 与具体 development；额外检查同 repository 的全量已报道 development key，防同 tag/同进展删除重发新 Release ID 重获机会。相同 event 后来编辑说明，只在确有此前未报道的重大变化、与旧投影比较并得到 new-material 判断时才有新 development。

规范化仅对评估出的语义字段使用既有事件投影相同的 NFKC/空白收敛；不对 opaque ID 或项目版本字符串随意改写。语义同一性的外部判断限制需要明确报告，固定替身不能证明真实模型永远正确。

### GHSA

上游 event key 为 repository node + GHSA ID；CVE 不替代 GHSA。仅 reviewed、未 withdrawn、severity high/critical、已核映射和明确受影响范围可作为风险更新。malware、未知类型/风险或冲突继续隔离，不转作项目推荐。

首个有完整范围的 GHSA 可以建立初始 risk development。排序后保存 package ecosystem/name、原始 vulnerable range、first patched version、severity、withdrawn 等源投影，保持 null/空值区别。相同材料重排/改名/updated/credits/CVSS分数微调不能产生新发展。

新增受影响产品、范围实质扩大、high→critical、明确新增修复/缓解是允许重新判定的变化类别。非平凡范围等价和改写不靠全文 hash 判断，需同一外部 verifier 比较旧/新投影；缺比较证据保持 revision-unconfirmed。A→B→A 查询全量已报道 development，不只比较 lastRevision。severity 降级、撤回停止绕过并显示风险状态/交给后续更正流程，不声称本票已经实现 #20 的更正发行。

#### Root 已批准的 GHSA 首版具体增量（2026-09-07 接续，尚待逐片实现）

来源权限拟增加可选、无默认值的 `events.allowAdvisoryBodyProcessing`；只有明确 true 才可读取含 description/summary 的官方响应，既有 `allowAdvisoryMetadata` 不能扩大成正文处理权限。同样受通用 collection/storage/model 字段、TTL、派生分发、引文额度及递增 Source Policy 版本约束。`DevelopmentConfiguration` 增加可选 `advisories`，缺失视为未启用但不向旧 JSON 写入默认字段，启用须提升配置版本。

固定只采 global 表示。发现入口 `GET /advisories?type=reviewed&sort=updated&direction=desc&per_page=min(30,maxItems)`，最多 3 个经允许列表核查的 cursor 页；补查当轮最多 50 个已核 node 上历史已发现的最多 50 个唯一 GHSA，使用单个 GHSA GET，监测降级/撤回；同 ID 同轮详情为当前权威，列表与详情内容冲突则该 ID 保留 conflict，不任选有利版本。分页、主动截断、未覆盖已知 ID 与请求失败分别留 Gap。无匹配公告或请求缺口只披露覆盖不足，不宣称安全；已明确关联但 scope/类型/severity/状态无法确认或互相冲突时隔离对应 node，不能继续普通入选。没有 node 映射的公告不从包名或引用猜关联，不授予任何项目事件资格。

永久安全证据投影保存 GHSA、`sourceRepresentation=global`、type、severity、published/updated/withdrawn、两个明确映射字段及核验 node 收据，和完整有限 vulnerability 条目：ecosystem/name、原始版本范围、first patched version、函数信息及 null/空值区别。按字段元组排序只去重完全相同条目，不重写范围语法、包大小写或版本；summary/description 全文仅短暂进入有权 verifier，归档只保留受引文总额约束的短摘录与具体影响范围。CVSS 数值/向量不是新的 scope 或严重性门槛，不自动取最大或推导缺失 severity。安全证据资源超限停止该关联 node 的风险资格并明确缺口，不保留截断后看似完整的 scope。

允许的实质修订固定为：初次完整高危/严重风险；新增明确受影响包；已有包受影响范围实质扩大；high 升为 critical；此前未披露的明确修复/缓解。每次修订收据必须引用真实先前同 node+GHSA 的可用投影，保存变化字段的 old/new 值、对应证据和 verifier 的 supported/new-material 判断。确定性程序核对字段确实改变且类别对应；版本范围等价、扩大和自然语言缓解是否实质仍是外部语义判断，结构匹配不是语义真值。无旧比较证据则 `revision-unconfirmed`，不得以新 hash/updated/标题/credits/CVSS 微调认定新发展。

同 node+GHSA 的全部历史 material development 与其风险投影用于重复抑制：完全等价投影直接复用旧身份，语义同一引用旧 development，A→B→A 的 A 回退不可复获资格，global/repository 交替输入不生成新发展。新修订的 development 身份绑定 GHSA、变化类别及规范化的具体风险变化；成功消费仍只来源于真实 Report10 INSERT。变成 medium/low/unknown 或 withdrawn 不授予事件绕过；withdrawn/unknown/冲突保守隔离，降级但范围仍明确则披露降级状态、按普通关注规则竞争，绝不称风险已消失。

事件竞争为 security → release → momentum；仍只恢复 recovery，保留频率和质量/新颖配额。安全入选在正文标“风险更新”，列明公告声明的受影响包/范围/修复状态、原始链接和缺失信息，并明确没有执行候选或提供安装建议。风险状态缺口在正文可见。Root 已批准上述共享 Schema、修订类别和隔离范围，产品仍须逐片 TDD 落实。

批准附带的精确条件：初次完整风险不要求不存在的 previous；已有同 GHSA 历史而不可用时保留 unknown，不能冒充初次。两条映射线索分别核到 stable node，改名同 node 不算冲突，无法核查不能任选；详情也不能吞掉 list/detail 冲突。known GHSA 来自跨全部已核历史、逐原来源有权且完整的集合；超过 50、失败或未覆盖的已关联 node 隔离并显示 Gap，旧 good 不复活。漏洞条目、短投影、assessment 每维独立有界，超限整条关联风险关闭，不按截断 scope 给完整结论。途中 advisories 配置/正文/旧投影撤权、cutoff、降级/撤回、表示切换与冲突分别以公开用例验证。

### 极端动量：拟比较后的推荐候选

这里暂提出 `P>=0.975`、有效 peer 至少 20 个、stars 24h平均净增至少 100 或 forks 至少 20。采用满足对应绝对下限的同一信号分位，不能 stars 达下限而靠 forks 分位拼接资格。只接受完整 measured 双点；cold、缺样、当前隔离、查询/候选上限截断或本轮排名输入不完整均无极端资格。

分位继续使用 Heat 的正信号中位秩算法。极端比较总体独立于普通最小 cohort 4：先 language+age，少于 20 回退 age，仍不足回退全部 measured；最终不足 20 明示 minimum-sample Gap。保存精确 peer node IDs、全部双点与实际间隔，不声称统计显著性或全 GitHub 极端。

拟使用可回放 episode：首次完整 extreme 观察开启 episode，event key 绑定 stable node 与该首次进入的原始 observation 身份。连续 extreme 保持同一 key，不能按日/新样本/改名/配置更新换 key；缺样、失败或不完整中断不能重新武装。一个 episode 只有固定 `initial-exceptional-momentum` 实质 revision，不把期间更高峰值额外当新修订。

重新武装条件拟为连续至少 24 小时完整、合格但不 extreme 的观察序列：相邻样本实际间隔不大于 90 分钟，整个序列覆盖不少于 24 小时，期间任何 extreme 重置退出计时，缺样/间隔超过 90 分钟也重置退出计时。之后再次 extreme 才开启新 episode。历史状态继承所有同 node 已核观察，配置/名称变化不当作退出；来源失权不能抹掉已开启 episode。

状态输入保存 previous episode/onset、逐步极端计算证据、退出序列和当前判断；重算验证 transition，不用一个自报 `isNew`。对一个待出版仓库的过长/缺失历史证明必须标 event-history-incomplete 并停止该动量绕过，不猜初始状态。拟单次最多保留/重放 2,160 小时 transition，退出证明最多 26 个小时点；超界不删长期消费身份，不把截断当新 episode。具体持久状态/证明布局需在实现首片中保持同一深 Module，避免把 episode 状态机外露给调用者。

## 5. 分数、竞争、质量与实际配额

保留每个候选旧 Heat 的 base/interest/recovery/frequency/ordinary score、原资格理由，以及每个事件 eligible/consumed/unconfirmed/blocked 的理由。满足来源、节点、当前仓库资格、年龄、topic、正关注质量、历史条件且存在未消费事件时，有效分数为 `base * interest * 1 * frequency`；只绕过 recovery，frequency 仍真实计数。

## 1. 已有契约与必须保持的事实

- `AgentRunner.run(ProduceRequest, {signal})` 是不可信外部输出 seam；Codex/Claude 当前只输出单 Edition Claim v2。CLI taskId 最大 200；不能直接把最长父 taskId 加 Edition 后交给 CLI。
- `EditionRunner.run(SixEditionRequest, {signal})` 返回六个 Edition 状态；Observer 已要求结果 taskId 为 `parent:edition`，这是上层 envelope，不能混同下层调用 ID。
- 两个 Runner 当前全部失败 `retryable:false`；新路由按下述版本化失败分类控制替代，不修改旧失败语义、不靠这个 bool 推导故障政策。
- 原 Observer 无 EditionRunner 或其抛异常会整期失败。新路由必须把局部失败收敛为六栏终态；缺少全部 Provider 也不是抛异常的借口。
- `SemanticVerifier.verify(VerificationInput)` 与 Publication Gate 是独立契约。Schema、哈希、Provider 一致不证明事实真实；当前高风险独立来源、财经一手交叉核验、社会样本、GitHub 资格/事件消费都不得被路由绕过。
- Final Editor 当前是 `sixEditionMarkdown` 及 GitHub 派生 Markdown 的纯确定性函数，已有 Today Overview/跨栏指向。保留这种实现，不增加任意成稿模型。
- #13 最新验收已在实际 master 完成 403/403、smoke 3/3、专项和旧刊复放，Issue 已 CLOSED；这些是基线证据，不算 #14 验收。

兼容冻结：旧 Request1–8/Record1–9/Version1–8/Canonicalv1–v7，及新基线 Request9/Record10/Version9/Canonicalv8，均保留既有输入、评分、正文及归档字节。尤其 Record10 实际入选节点必须继续计入旧 Request8 普通 Heat 历史；长期已消费 Release/GHSA/momentum 不截成 90 天，不 backfill、重装、重写 olddata。原 publication 同步事务与 DevelopmentHistoryReadScope 的同步只读复核保留。

## 2. Interface 与版本增量提案

新增深 Module `provider-routing.ts`，集中管理路由、资格、执行预算、失败替代和决策收据；不把这些分散到六个 Edition 调用点。

拟公开 `createProviderRouting(options)` 返回 `run(request, {signal})` 与 `verify(input)`，分别接入现有 EditionRunner、SemanticVerifier seam；`Observer.readRun(runId, ownerToken)` 是无发布或双失败时仍可查询的鉴权审计 seam，复用实际 Owner token 校验。相同读取权限适用于成功和失败记录。同一 run 的研究与核验共享受信 deadline/预算，绑定 taskId、Bundle ID、配置摘要、父 runId；不能用全局“最近一次 run”或裸 taskId 查可复用结果。装配时为每次 produce 创建绑定 run 的 adapter，由 Observer 在 finally 封存终态；不允许调用者自己拼接另一轮 verifier。

Provider 配置包含 codex/claude 各自按六栏的既有 AgentRunner 及受限语义核验 Adapter。研究结果严格校验 Provider、model、时间、CLI终态、退出、cleanup、Edition、Claim/Evidence 成员后才能作候选。若具体核验适配器需要扩大现有 CLI 输出 schema，将新增独立受限任务模式，复用同一容器/broker，不改变旧 CandidateOutput/AgentRunner 契约；实际 schema/接线须在进入该片前给 Root 阅读。

资格与配置来自受信装配，不接受 Request/模型 JSON 自报。新调用 ID 固定为 `route-` 加 SHA256([runId, parentTaskId, edition, role, provider, attempt])，长度 70；完整身份关系保存在受信 receipt。校验原 AgentResult 对应此 ID 后，仅在内部投影为已有 `parent:edition` envelope；原 AgentResult 元数据保留独立收据，不能伪称 CLI 原本返回长 ID。

建议新 Request10 → Record11 → Version10 → `observer-canonical-v9`，只新路径携带 routing 和 Final Editor 元数据；不得给旧 Schema 添默认字段。Record11 继承 Record10 的全部社会、兴趣、事件、GitHub、长期消费事实，增加 routing 收据及其完整性约束。旧 reader/renderer 保持原分支；新 read 重核 routing 与原候选/Gate 决策、六栏及 Final Editor 输入摘要的关联。新 Record11 同样参与旧请求普通历史和新事件历史；不能因版本号跳过。最终序号须 Root 批准后才写 contracts。

路由审计保存在 Report 数据库的新增独立表 `routing_runs`，新增 nullable reports.routing_capture_sha256 作为独立出版关联和安装见证；旧payload/Record字节、旧行NULL不backfill，SQLite user_version不改。未安装旧DB的只读装配不创建路由结构；已安装结构损坏使createObserver明确unsupported-routing-storage，包含只读装配，不能静默重建。只保存有界安全状态、身份、配置快照摘要、已投影 usage 和 terminal；不记录错误文本、模型原文、秘密或来源正文。失败没有Report时仍有独立安全运行收据；成功Report保存实际采用各栏的决策、复核/仲裁及FinalEditor收据与run身份，独立记录保留所有失败尝试。读回关联以真实存储行和冻结输入为准，哈希仅检一致性。当前 `main.ts` 继续只读/publication disabled；不新增HTTP发布路由或启动日调度，#15负责调度和恢复发布。

恢复裁定（Root，168后）：#14不自动启动写入、不全库标abandoned，也不新增Owner认领/lease。readRun的running/ready只是last-observed事实，不证明进程仍活跃或cleanup已证实，不能据此释放旧槽、接管其他writer或重放publication。受控成功/失败/取消仍须记录终态，终态存储不可覆盖；跨实例恢复/fencing按原#15/#23任务设计落实。此裁定取代初稿重启abandoned设想，不把恢复计成本票已验收。

## 3. 资格、任务路由与主备互换

ProviderEligibility v1 拟有 version、provider、enabled、accountEligible、regionEligible、checkedAtUtc、validUntilUtc、evidenceReference（非秘密操作记录 ID）。缺失/unknown/到期/撤销禁用该 Provider；不能凭已登录、CLI版本、技术连通或 fixture 凭证判定合格。每次外部调用前后及发布前复核当前资格与同版本配置摘要；版本回退或同版改内容拒绝。资格失效取消该 Provider 在途任务，其他已完成且仍合格栏可保留。

测试使用显式 `protocol-fixture` 资格范围，只允许 Owned 协议替身，不声称真实账户/地域合格。本机真实地区尚未知；Claude live owner-deferred / NOT VERIFIED。当前不启用真实 Provider 或生产。

路由规则 `observer-routing-v1`：每 Edition 配置 primary=codex 或 claude，backup 为另一个；默认全栏同一 primary，但可逐栏配置。固定六栏顺序与队列，并发不由 Edition 数量推断。无证据直接 no-evidence，不调用模型。主资格不合格记录 disabled 后直接选合格备；正常主成功不发起第二份完整研究。

状态：queued → eligibility-checked → primary-selected（或 backup-selected）→ attempt-started → succeeded / failed / cancelled。需要备份时显式 fallback-selected，再进入独立 attempt。每个状态记录 sequence、runId、Edition、role、Provider、bounded attempt ID、时间、稳定 reason、实际 usage 与清理终态。终态包括 research-completed、review-required、review-completed、review-unavailable、disputed、no-provider、cancelled、deadline-exceeded、usage-anomaly、cleanup-unverified；不只存最终字符串。

失败替代：unavailable、timeout、nonzero-exit、invalid-output、version-mismatch 可尝试另一个合格 Provider 一次；输出超限可替代一次但仍计原用量。input-limit、evidence-expired、source/资格失效先按真实原因降级，不给另一 Provider 发送同一非法输入。policy-violation 隔离本次结果并禁用该 Provider 本轮余下任务，完成可信清理后才可由备 Provider 重新从原合格 Bundle 开始。cleanup-failed/unverified 不启动更多进程，整轮停止新调用并保留已完成安全栏。显式 Owner 取消/全局 deadline 不启动 fallback。unknown 外部异常记录无正文原因，允许一次备份，不无限重试。

同 Provider 重试默认 0，可配置最多 1，仅 transport unavailable 且无取消/策略/清理错误时启用；与最多两个 Provider 的全栏尝试总限共同生效。禁止 A→B→A 循环。主备交换对称，不为 Codex 添加额外出版权威。

## 4. 高风险复核、分歧及 Publication Gate

正常研究一次；普通语义核验仍必需，是对 Claim/Evidence 的评估，不是完整第二份研究。使用被选研究 Provider 的语义 Adapter 执行当前最多 500 assessment 的 whole-story 批次，保持最多 30 批的既有完整容量。

触发另一 Provider 条件复核：首次完整且有效 assessment 中 risk.level=high、conclusion=conflicting、任一证据 contradicts；risk unknown 或缺少必要 domain 的候选继续按现有 Gate 隔离，不能把“未被识别为高风险”当已验证低风险。触发只来自已核输入/assessment，不信 Candidate 自报“无需复核”。复核输入只投影有关原 Claim、其允许 Evidence 和身份摘要，不附任意新网页或要求再写整栏。

第二 Provider 对相同 Claim/Evidence 独立给完整评估，保留两份原始结构收据和 Provider/role/输入摘要；其投影不可伪装成某一 Provider 原生 receipt。任何评估都不能扩充输入外 Evidence，新增来源必须走既有配置采集流程，并留下一期或专门纠错流程。

仲裁 v1 采用保守确定性收敛，无第三轮投票、无人工 override：逐 Claim 比较结论、归因、支持/反驳关系、独立上游身份、风险及必要 domain/事件/选题语义字段；无关序列差异先按稳定 ID 对齐。关键字段不一致 → disputed；安全/许可/结构失败 → quarantined；能够安全归因但证据不足或冲突 → unconfirmed。原 Publisher 声明只证明声明；两个 Provider 同意或两个域名转载同一 upstreamOrigin 均不解除独立来源要求。

两评估关键字段一致，也必须重新经过既有 Publication Gate 高风险两独立可靠源、财经一手支持、引语及域规则。缺第二 Provider 时保留 `review-unavailable`、单 Provider 范围：若完整主评估及既有严格证据门满足，允许单 Provider 结果并明确没有双复核；未满足不得发表。这个单 Provider 取舍需 Root 确认，不把复核缺失静默称一致。

新 Record 的 routed gate 保留 primary/review/arbiter 三类 provenance，最终 Gate 决策引用实际收据身份；不得合成 `research-agent` receipt 冒充 Provider 原输出。事件/兴趣/社会/GitHub语义投影仍按原可接受收据及其真实历史规则生成，争议影响的 Claim 不留成已发表关联。没有网络补证或投票解除 disputed 的路径。

## 5. Final Editor、失败保留与采集可用性

新公开 `finalizeRoutedRecord(validatedRecord)` 只接受新路径已完成 schema、来源许可、Gate、跨栏事件、兴趣、社会及 GitHub 同步 authority 核验的 Record，内部再核内容一致性；返回 Canonical Brief 及 receipt `{contract,inputRecordSha256,capabilities:{network:false,shell:false},status}`。它是纯确定性 Module，不注入 Runner/transport/FS/时钟/工具注册，不读取原 Bundle 或未核候选。既有生成器复用受校验投影，保持原 Claim 字节、引语、数字和来源，不写新事实。新 receipt 摘要排除 receipt 自身以避免循环哈希，版本绑定在最终 PublishedReport。绕过 Observer 直接传 malformed record 必须拒绝。

Final Editor 不足以提供原文许可和真实历史 authority，因此公开 finalize 只证明局部一致性，最终 publish/read 同步复核仍不可省。失败不回收已完成 Edition；返回完整六栏、无摘要的原因与已校验栏快照，由后续调度票决定链接版/迟到/恢复窗口。

研究可用性与采集可用性分开：每栏记录 research succeeded/failed/no-evidence，collection available/partial/unavailable，以及基于真实允许分发元数据计算的 linkEvidenceIds、来源缺口。不能从“模型失败”推断采集不可用，也不能从只有 model-forbidden 的 Bundle 空投影推断无可分发链接；保留采集原安全身份投影，按当前 distribution 权限独立筛选。全 Provider 失败且有合格链接 → agents-unavailable-collection-available；无合格采集 → agents-unavailable-collection-unavailable，partial 单列。无中途 stdout、无造摘要/分析。此票只提供消费结果；正式 links-only 刊、恢复时窗与投递属于调度票。

## 6. 调用与异常用量参数版本（待容量回放批准）

参数版本拟 `observer-routing-limits-v1`，可配置值必须通过有限整数/范围及总预算一致性校验，记录实际生效配置及摘要；不设日/月/美元业务预算封顶。以下为初始工程提案，不能称已经容量验证：

| 限制 | 初值 | 范围与计数语义 |
| --- | --- | --- |
| 整轮 deadline | 900000 ms | 1000–3600000；包含排队、研究、复核、Gate、Final Editor；单调时钟计时 |
| 每次 Runner | 60000 ms | 100–300000，取剩余总 deadline 与本上限最小值 |
| 在途进程/外部模型请求 | 2 / 2 | 各 1–4；研究与核验共享，不各建独立池 |
| 每栏研究 Provider 尝试 | 2 | 最大 2，另有同Provider retry预算；总研究进程最多24含重试 |
| 同 Provider retry | 0 | 0–1，仅上文可重试类别；重试也消耗所有计数 |
| 每次进程 model requests | 4 | 1–8，保留现有 Runner 硬界；开始调用前扣额 |
| 语义批次 | 30 主 + 30 复核 | 每批≤500 assessment，不降低6×50 stories×50 claims容量；无第三仲裁模型 |
| 整轮外部请求 | 336 | ≤(24+60)×4 初值，含失败请求，不退款；可配置但有限，验证组合可达性 |
| 单次输出 | 2 MiB | 既有1 KiB–8 MiB硬范围；跨调用安全审计另上限 |
| routing-v1 安全审计硬限 | 64 MiB | Root批准；写入与只读装配读取均按实际 JSON UTF-8 字节限制，绝不信 receipt 自报无限上限。低配置预算及派发前预留另作纵片验证 |
| 异常累计可观测 token | 2000000 | 单轮观察保护，非美元/业务预算；输入/输出加和不再重复加缓存或reasoning子集 |

当前容器 broker 已可并发处理请求，新增全轮控制必须在 trusted transport 实际 dispatch 前保留配额/并发位，资格/来源/剩余deadline前后检查；只统计最终 AgentResult 不足以控制在途爆发。SemanticVerifier 现无 AbortSignal 需新增版本化可取消调用 Adapter；旧接口保持。超时先 abort，再等待原容器 cleanup readback；计时到期不能把 Promise.race 返回当清理完成。忽略 signal 的不可信外部响应不得写回结果；无法确认清理记录 cleanup-unverified，禁止后续调用。清理本身继承现有有界过程，receipt 分开记录工作deadline和额外清理耗时，不能声称deadline包括无限清理。

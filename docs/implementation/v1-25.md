# V1-25：影子评测归档、事实表与续采

实现采用 implement 技能；Owner 的 RAPID V1 明确覆盖该技能的逐步 TDD、反复检查、全套测试与自行委派 review。Root 承接一次短静态 Standards/Spec review。本票没有启动 campaign、签署核查规则、运行真实 Provider/来源/SMTP/S3/Docker、读取任何 Owner 配置或秘密，也没有操作旧数据库/样本。默认 `enabled:false`，未接入日常服务启动。

## 已交付边界

`src/shadow-contracts.ts` 固定规则版本与 CLI 输入契约；`shadow-sampling.ts` 从完整当前六栏建立样本；`shadow-evaluation.ts` 持久任务、统计、清理及真实可读检查；`shadow-admin.ts` 提供 `npm run shadow -- ...`。这是评测管理工具，不是新的新闻生成器；正式的 `production` / `test-fixture`、`live` / `protocol-fixture` 边界完全不变。

评测 DB 固定为专用目录中的 `shadow.sqlite`，使用独立 `application_id=1329746771`、schema 1；拒绝已有未知库以及与声明的 production data 目录重叠/嵌套，拒绝 DB 符号链接。目录路径在配置加载时解析实际父目录。此库没有 `reports`、邮件 outbox、凭据/设备表，也不打开正式报告库。两个 Provider 的 HTTP 地址不能相同。实际 #27 运行仍必须把两个生产模式实例的 DB、collection、GitHub、taskRoot、端口和秘密都放入各自隔离评测环境，关闭 email；不能把正式服务地址填入 shadow server。路径配置是操作者受信输入，并非对任意网络服务的归属证明。

campaign 保存日期区间、scope、实际 code release、Report Record applicationVersion、两 Provider 的模型/CLI/runner 版本及明确的核查人/核定时刻。规则只能使用当前固定版本；改变规则、代码或比较配置应另开 campaign，不能修改已有日期。一个 campaign/业务日只有一个 batch；同日两个 job 引用同一个已解析冻结 ScheduledSnapshot、规则和输入指纹。该 SHA-256 是票要求的产品输入身份，不是开发验收取证。Bundle、配置与版本保留在短期材料中；普通原始字段必须获得 collection/storage grant。

唯一 treatment 为所选 Provider 的 research 与 routing primary；允许现有复核角色按已有 routing 规则运行。Complete 要求声明同一指纹及 code version、同一任务/日期/Bundle/config ID、同一兴趣配置与 routing limits，以及每个实际 edition result 的 Provider、model、runner、CLI 身份；live 样本还要求 scheduled provenance 和现有真实 CLI/API/容器清理元数据。输入中的普通证据归属/实际可见元数据必须与冻结内容一致。指纹/版本声明是受信运行接线的交接记录，不是独立证明模型真正看过哪些字节；#27 需要直接把 start 输出交给已有真实运行边界，不能人工构造一个“真实”回执。

## 配置与操作

以下路径是说明示例，不是已部署文件。非秘密配置 `shadow.json` 的字段为：

```json
{
  "schemaVersion": 1,
  "enabled": false,
  "directory": "/srv/observer-shadow/evaluation",
  "productionDataDirectory": "/srv/observer/data",
  "sourceConfigurationPath": "/etc/observer/config/sources.json",
  "rightsContractPath": "/etc/observer/backup-authority/rights.json",
  "servers": {
    "codex": "http://127.0.0.1:3101/",
    "claude": "http://127.0.0.1:3102/"
  }
}
```

现有最新 SourceConfiguration 和 #22 删除契约都是必需的权威输入；缺失/不可读不当成空。`rules` 不打开库；`maintain` 和 `watch` 即使 enabled=false 也可清理。其他采集/评测写入及真实 probe 要显式 enabled=true。仅 `probe` 读取 `OBSERVER_SHADOW_CODEX_OWNER_TOKEN[_FILE]` 或 `OBSERVER_SHADOW_CLAUDE_OWNER_TOKEN[_FILE]`，复用 #23 专用文件优先的 secret 读取机制；不读取正式 Owner/API/QQ_SMTP_KEY。此工具不构造 Provider，不自动读取 Provider API key。

```sh
npm run shadow -- --config shadow.json rules
npm run shadow -- --config shadow.json campaign campaign.json
npm run shadow -- --config shadow.json freeze freeze-day.json
npm run shadow -- --config shadow.json start start-codex.json
npm run shadow -- --config shadow.json complete completed-codex.json
npm run shadow -- --config shadow.json probe start-codex.json
npm run shadow -- --config shadow.json form <attempt-id>
npm run shadow -- --config shadow.json review human-review.json
npm run shadow -- --config shadow.json status <campaign-id>
npm run shadow -- --config shadow.json export <batch-id>
npm run shadow -- --config shadow.json export <batch-id> --material
npm run shadow -- --config shadow.json maintain
npm run shadow -- --config shadow.json watch
```

`campaign.json` 为 `{id,startBusinessDate,days:14,scope:"live",codeVersion,applicationVersion,rulesVersion:"observer-shadow-v1-draft-1",approvedBy,approvedAtUtc,providers:{codex:{model,cliVersion,runnerVersion},claude:{model,cliVersion,runnerVersion}}}`。`codeVersion` 必须等于冻结 snapshot 的 `versions.application`（部署 release）；`applicationVersion` 是 Record 实际写入的版本，目前代码为 `0.1.0`。两者不是同一个字段。核定人和时刻必须由真实操作者填写，本票没有代签；提供这组字段不是自动取得资源/真实运行授权。

`freeze-day.json` 为 `{campaignId,batchId,input:<FrozenShadowInput>}`。input 是 schema 1 的完整 ScheduledSnapshot：request、policies、interest、discourse、github、routing、configuration、versions、frozenAtUtc；configuration 使用严格的非秘密 ProductionConfiguration，request 的 discourseSamples 使用真实 DiscourseSampleSchema。request 必须为 schema 10、Bundle 为 collected schema 2，cutoff 为业务日上海 07:30。已有 source field grants 仍适用；不要把环境、凭据或自由配置混入 snapshot。

`start-codex.json` 为 `{batchId,provider:"codex"}`。start 原子认领，返回 `{attemptId,provider,ordinal,leaseUntilUtc,inputFingerprint,codeVersion,input,treatment,output}`；其中 input 是共用冻结内容。claude 使用同一 batch 和 `provider:"claude"`，不能重新采集/重新冻结。租约不超过一小时、来源 TTL 和当天 12:00；过期任务变 interrupted，保留失败身份，再次 start 同批同 Provider 续采。显式失败入口：

```sh
npm run shadow -- --config shadow.json fail failure.json
npm run shadow -- --config shadow.json start start-codex.json
```

failure 为 `{attemptId,reason,costUsd:null}`，reason 可选 unavailable/timeout/invalid-output/process-failed/interrupted/policy-blocked。失败次数与所有 attempts 保留；未知 cost 是 null。工具不会杀掉已失联的外部 Runner，#23 的进程/容器截止仍由运行器负责。第一次成功 complete 后该 Provider job 不再允许 start，避免把较差结果删除后只保留最好一次。失败后超过中午或来源失效不能用新材料冒充同一冻结日续跑，应记录缺失并进入下一业务日。

## #27 的真实运行衔接

#27 负责获授权后的真实采集、两个隔离 production-mode 运行实例及每日触发。具体接线为：每天从一次获准采集取得冻结 snapshot → `freeze` 一次 → 为每个 Provider `start` → 将返回的 input 原样交给现有 Observer scheduled 运行边界，所选 Provider 仅改变 routing primary，并只启用该 Provider 的研究 Adapter → 从该隔离实例的权利检查 reader 取得 PublishedReport 与所需历史版本 → `complete` → `probe` → 人工 form/review。不把 `mode` 改成 fixture，不导入正式邮件 outbox，不在 CLI 中执行未审脚本。构造隔离实例与传入现有 `scheduledStore.freeze` / `runScheduled` 的组成由 #27 承接；本票没有另造通用 Provider launcher 或调度器。

`completed-codex.json` 为 `{attemptId,inputFingerprint,codeVersion,report:<PublishedReport>,history:[<PublishedReport>...]}`。history 必须完整包含当前版本的前驱链与栏目实际 sourceVersion；缺版本、重复身份、环、继承栏目 Markdown 不一致拒绝。Complete 抛错时 job 在租约内仍 running，可以修正格式重新 complete，或使用 fail 记录真实失败后再 start。上层运行器可以直接调用导出的 `openShadowEvaluation` 同名方法传递内存对象，避免磁盘交接文件；外部程序应捕获错误并在尚持有任务时 fail，不能吞掉失败。

这条路径的持久恢复点是 SQLite 中 campaign、batch、jobs、attempts，而不是 agent 上下文。新上下文先 status，查未完成 Provider 和已有 attempt ID，再按上述入口继续。没有本文以外隐藏的一次性启动脚本。#27 仍须完成真实 Provider 接线并记录首个运行证据；本票的管理入口不表示 #27 已开始。

probe 只向配置的 HTTPS（或本机 HTTP）隔离 Observer `/v1/reports/<version>` 发送鉴权 GET，拒绝重定向、非成功响应与超限正文，解析完整 PublishedReport 并与该 attempt 保存的内容逐字段比较；只有成功读完后才记录主机当前 UTC。不能由用户传入一个更早 readableAt，也不使用 ReportVersion 生成时间或邮件受理时间。第一次成功 probe 时刻固定，后续检查不改写；若检查晚到，记录的是保守的实际观察时间，不能倒推服务早已可读。

## 抽样与人工事实判定

普通 Priority 取 `editions.priorityStoryIds`，Watch 总体取实际 storyIds。社交使用独立 observations 的 priority/story，附样本边界字段；GitHub 从实际 repromotion/ranking selectedNodeIds（旧版 watchItems）取 Watch，使用真实 Canonical Markdown 中项目段落，完整排名/重大进展附录另设必查项。普通故事还包含 Event Cluster 的 supportingClaims。Completion 沿 `correctionSectionSource` 查前驱栏目；Correction 使用 `revision.inherited[].sourceVersionId`，并用 `editionMarkdown` 比较当前实际全文片段。不会只看最新 record.stories。

所有 Priority 入样，Watch 使用冻结的随机 uint32 seed、LCG + Fisher–Yates、`ceil(N*0.2)` 无放回抽样。保留总体顺序、总体数、重点数、Watch 数、抽样算法、seed、实际集合。两 Provider 共用 seed/算法，因实际输出条目不同各自计算分母，不强行把缺失故事配成相同 ID。追加的 GitHub 附录必查项与更正必查项不是额外 Watch 分母。

每个选中 Claim 都有独立 key、原陈述及对应证据引用；fact/statement/quotation/analysis 都进入表，quotation 同时展示原文、statement 展示发布者。核查者把复合句分为可独立判真的事实，逐项保存 text、verdict、evidenceRefs、basis、fabricatedSource、seriousError、wrongAttribution。发言归因本身必须核查；“X 声称 Y”不能因为仅核实 X 确实发言就把 Y 统计为已证事实。解释或情景里的事实前提也切出。GitHub rendered 段落逐项切分身份、存量、净增、时刻、排名与发布者声明。重复标题/引用同一句不再次加入事实分母；同一故事独立的 supporting claim 则照常核查。页面其它标题、时间/样本说明和 Impact Note 需要结合 form 的完整 Canonical Markdown 检查，将额外事实归入所属样本的 facts，不用链接打开数量替代。

表单允许 `finalized:false` 保存部分人工工作，后续 review 替换草稿；最终 `finalized:true` 后不可覆盖。missing Claim 在草稿中保持 incomplete；提交最终表必须覆盖所有选中 Claim。真正没有事实的 analysis/rendered 项必须填写 noFactReason；fact/statement/quotation 不能借空列表逃避核查。支持判定至少引用批次已知证据 ID，并提供 basis；伪造/严重错误/错误归因不能同时标 supported。工具核对身份与计数，无法证明人工评语本身正确或证据真的支持语义。

事实分母是最终人工枚举的全部事实，unsupported/conflicting/unverifiable 都不进入 supported 分子。零事实比例为 null；空样本、没有完成分句/人工核查为 INCOMPLETE。live 且有模型内容、结构/来源政策检查全部满足、零伪造/零严错、支持率 ≥98%、完整人工核查及输入可比才生成当前样本 `modelQuality:PASS`。明确失败项为 FAIL，fixture 和模型不可用/links-only 为 NOT_APPLICABLE。新 Correction 带原冻结输入之外的补充核验材料，仍能生成完整事实表，但 `inputComparable:false`，不产生同冻结输入质量 PASS；应单独解释补充输入，不能混入初始 Provider 对照。单 Provider 样本明确列缺另一者，两个都没有模型只表示 no-model-quality-evidence。

人工作品级指标包括 omissions、duplicates、classificationErrors、expression（clear/minor-issues/major-issues）和 notes。零值必须是人工观察；空值保留在未提交模板。统计同时保留伪造、严错、错误归因、支持/核查事实数、缺失 Claim、每次失败、运行段耗时、实际 CLI 累计耗时与失败数、已知 USD 及未知成本 attempt 数。已知部分成本不是总成本；未知成本绝不补成 0。

规则草案中的严重错误例子：把国家/人名/关键日期/数量写错并改变结论、颠倒因果、把未经证实的安全或金融结论写成事实、错误归因重要言论；伪造机构、URL 或并不存在的原始出处单独计数。核查者应在 campaign 前核定这些定义与上述事实切分、20% 取整、同日比较、空样本/无事实/人工缺失/失败重试/未知成本口径。当前版本名保留 draft，campaign 中的真实签署固定采用这个版本；本票不声称人已核定。

## 准时、保留与导出

按日期/Provider 分别列 normal-on-time、degraded-on-time、late、missing、pending。实际 live probe ≤08:30 分为正常/降级准时；08:30 后且中午前为 late；截至 12:00 未取得实际 live 可读证据为 missing，后补 probe 不抹掉这个结果。fixture probe 可保存观察时间，但不计真实准时。没有创建 batch 的日期也显式列 missing/pending，不能通过不建任务排除失败日。状态给出两 Provider 各类天数，不替 #28 输出 release verdict。

所有 snapshot、原文、报告、引文、人工事实/自由文字同批采用保守最短材料期限：最多 30 天、每个冻结来源的 retentionHours，以及所有显式 expiresAtUtc 的最小值；通常会远短于 30 天。每次读取/写入前及独立 `watch` 每分钟读取最新来源/删除契约；策略变化、来源撤销、版本删除或到期会清空整批 source-bearing material 与指纹，保留脱正文数值统计/最小任务身份。对读取权威失败采取拒绝，watch 保持报错并重试；停机期间不会声称物理删除已经完成。永久来源/版本抑制不会因契约回退消失，权利删除后该批当前质量状态变为 INCOMPLETE。SQLite secure_delete、DELETE journal 和清理后 VACUUM 避免旧材料留在普通空闲页；没有遍历旧数据库或临时目录。

默认 `export` 仅返回脱正文批次统计；`--material` 才在评测目录创建登记 UUID 名的 0600 JSON，文件与批次同期限/权利规则，维护只删除准确登记的自产文件。form/start 会输出短期材料，调用方优先使用 API 内存交接；若重定向、复制到别处或人工另存，副本由操作者执行同样 TTL/权利删除，工具不能远程擦除。#24 普通备份不新增 shadow 数据；它不是长期原文副本。要积累 14 天数字，按日导出脱正文统计；正文过期前完成人工核查。尚未核查就过期的事实不能回填“已验证”。

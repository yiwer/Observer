## 已实现的链路

公开测试 seam 是 `createObserver(...).produce(input, { signal }) → readReport(version.id, ownerToken)`。Bundle、共有 AgentRunner、v2 候选解析、既有语义 Verifier 接口、Publication Gate、SQLite 原子归档和 Canonical Markdown 均在链路内。替换的是系统外的 CLI 协议进程或模型 Responses API，以及既有人工标注 Verifier；没有 mock 自己的 Gate／归档。

`createCodexRunner` 返回供应商无关的 `AgentRunner`。CLI 事件仅在适配器内部处理，业务层仍接收 `AgentResult`。一次调用只处理指定 Edition；没有新增调度、仲裁、部署或真实检索能力。生产装配继续 `publication-disabled`，测试归档对生产读取为 `not-found`。

## 实际权限与模型通道

每任务创建唯一容器，固定本地 Docker socket／Windows Desktop Linux named pipe，不继承用户 Docker context 或 registry 配置。宿主 Docker 客户端只保留 PATH、Windows 系统路径及临时目录环境；容器经 `env -i` 仅获得必要 PATH、locale、私有 HOME／CODEX_HOME 和线程上限，无 API 密钥、Owner 密钥或用户 HOME 挂载。

容器参数为 `--network none --read-only --cap-drop ALL --security-opt no-new-privileges=true --user 65534:65534`，并限制 32 PIDs、256 MiB、1 CPU。唯一可写区为 16 MiB 的私有 `noexec,nosuid` tmpfs，归 UID/GID 65534 所有、mode 0700。任务 prompt/schema 通过 stdin 投送，再由相同 UID 写入 tmpfs，不依赖 Windows bind mount 忽略权限的行为，也无需 chmod 777。只读挂载可信 supervisor；协议替身模式另外挂载测试程序。没有宿主根目录、用户目录、Docker socket 或业务卷挂载。

CLI 配置关闭 shell_tool、apps、web_search，空 CODEX_HOME 配合 ignore-user-config／ignore-rules，不载入用户 MCP。没有向模型暴露任何执行或检索工具。`noexec` 仅证明不能直接运行 tmpfs 程序，不能阻止受信 Python 解释器读取脚本；禁止候选代码运行的主要保证是：材料仅作数据、模型请求强制 `tools=[]`／`tool_choice=none`，返回的可执行工具项在进入 CLI 前即被拒绝，CLI 事件中的工具类型也不能成功。操作系统边界另外阻止宿主秘密、提权、配置写入和外部网络。

容器无外部网络，但不是永远不可调用模型的空壳：可信 supervisor 提供仅环回可达的 `127.0.0.1:8765/v1/responses`，通过 stdio 控制帧把模型请求交给宿主 `CodexModelTransport`。子进程 stdout 被嵌套为事件数据，不能伪造顶层控制帧。broker 仅接受正确 Host、POST、精确 `/v1/responses` 和固定模型；拒绝 CONNECT、其他主机／路径、MCP 和不合模型。宿主真实 transport 仅 POST `https://api.openai.com/v1/responses`，禁止重定向，不接受子进程给出的 URL、认证头或代理地址。

已实现的授权接入代码是 `createOpenAIModelTransport(apiKey)` 配合 `createCodexRunner({ runtime: { kind: "codex-cli", image: "sha256:..." }, transport, ... })`。API key 由后续受信装配显式提供，留在宿主，不读本机保存的 Codex 登录、不进入容器或任务材料。此次测试仅用 `model-protocol-fixture` 代替该外部 API；没有调用真实 transport。#26 仍需授权环境、账户／地区资格和真实模型实测，不是声称已连通。

模型发送最多默认 4 次（可设 1–8），单请求不超过 1 MiB，响应不超过 2 MiB；强制 `store=false`、`stream=true`、`background=false`。任务默认 60 秒（可设 100 ms–300 s），取消／超时同时中止宿主传输 AbortSignal 和容器任务。每次发送前使用 Runner 捕获的可信 Bundle v2 检查 `expiresAtUtc`，不相信 CLI body 中的新期限；受控时钟测试覆盖第二次请求到期拒发及两次未过期正例。

原始模型请求／响应不写业务日志。容器显式 `--log-driver none`，避免 Docker 默认日志驱动把 supervisor 控制帧另存或外发；实际测试在任务存活时核验自身唯一 taskId 对应容器，driver 为 none，`docker logs` 不可读取，而 attach 和归档链路正常。[Docker 日志配置依据](https://docs.docker.com/engine/logging/configure/)。宿主受信进程内存、内核／Docker daemon 管理员和部署级内存／交换区保护不由应用沙箱保证。

## 成功判定、清理与脱敏

只有退出码 0、单次完整 `thread.started → turn.started → ... → turn.completed`、恰好一个完成的 agent_message、匹配的 final 文件、严格 v2 schema 及 task/Bundle/configuration/Edition 身份全部一致时，才返回 succeeded。状态机允许有界 reasoning 进展但不归档其文本。缺终态、缺 final、部分输出、重复消息／终态、终态后事件／错误、未完成 item、未知事件、工具事件、非 JSON 和身份不匹配均拒绝，不能选取最有利的一帧。

stdout／stderr 共享默认 2 MiB 输出预算（可设 1 KiB–8 MiB），stderr 原文被 supervisor 替换为字节数后计入预算；终态结构中的候选才可进入 Gate。错误仅保留分类、版本、持续毫秒数、exitCode、terminal、容器身份及 cleanup；无原始错误文本／prompt／模型响应。已观察的 usage 字段包括 input、cached input、cache-write input、output、reasoning output；缺失值和费用为 `null`，版本缺失为 `unknown`，不伪造为零。

容器不可变 ID 是任务进程树身份；清理前核验 ID、唯一名称、任务 label、image ID、Created，使用该 ID force-remove 后再次确认不存在。不会按裸 PID、同名进程、全局 label 首项或全局 Docker 清空来清理。宿主只终止自己尚存的 Docker child handle。清理不可证实时失败为 cleanup-failed，不能发布。任务目录仅删除自身 mkdtemp 子目录，既不挂载也不保存 Evidence／凭证。

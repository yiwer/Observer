# V1-24：节点外一致性备份与干净恢复

本票交付实际 S3 API 接入、流式加密快照、受控 CLI、分钟触发与恢复演练记录入口。采用 implement 技能完成实现与提交；Owner 最新 RAPID V1 覆盖该技能的逐步 TDD、全套测试与自行派 reviewer 要求。Root 提供本票一次双轴短静态 review。本票没有操作真实对象存储、Docker、Owner 数据、Provider、SMTP、TLS、部署或本机登录文件。

## 协议与选择

选择一个明确的协议：HTTPS S3 REST API，通过固定依赖 `@aws-sdk/client-s3@3.1127.0`、显式 endpoint/region/bucket/prefix、path-style 与 expected bucket owner 接入。没有供应商购买、自动建桶、IAM 修改、服务安装或通用插件框架。其他兼容对象存储必须支持这里实际调用的 API；不支持时拒绝运行，不能用配置勾选“私有”来略过检查。

仅管理专用 prefix 下两个准确对象：`snapshot.obs` 是当前快照；`authority.obs` 是独立于快照的最新来源策略与永久删除契约。每次成功备份覆盖当前快照，**不保留旧快照历史**；这是 V1 的明确保留策略，不能用来恢复更早的误编辑。需恢复历史配置时另外保留无秘密的 release/config 版本，但不额外导出来源正文。

每次操作检查桶级 PublicAccessBlock 四项均为 true、PolicyStatus 非公开（明确没有桶策略也可）、从未启用版本化、没有 Object Lock 和桶复制。`Enabled` 和 `Suspended` 均拒绝；这避免 DeleteObject 只增加删除标记、锁定副本不能删除或复制副本逃出管理。桶管理员必须维持这些条件，禁止额外复制、对象锁、历史版本与其他程序写同一 prefix；程序没有这些管理权限。权限漂移或网络错误记录失败，不能据此宣称内容已删除。IAM、供应商内部副本/物理擦除与真实匿名访问的独立检查留 #26。

S3 默认无 ACL 的 PutObject 配合四项 PublicAccessBlock；不是把公开下载地址当私有备份。所有普通快照及 authority 对象另外使用独立随机 32 字节密钥的 AES-256-GCM，96 位随机 nonce、认证格式头和 128 位 tag。格式头 `OBSBK001`，认证内清单 schema 1，包含 snapshot UUID、准确 release/Node/configuration 身份、UTC 一致性边界、报告版本 ID、每个文件字节数及 SHA-256。AAD、文件清单校验和 SQLite 结构检查是**运行时产品完整性**，本票没有执行 hash 验收取证。

不使用 multipart，单次对象上限 4 GiB；默认总快照预算 1 GiB（含保守清单余量），可在上限内配置。加密、传输和文件完整性是流式，SQLite 逻辑复制逐行；单个报告/PDF 行仍需进内存。每个 S3 请求/下载截止 10 分钟、不自动重试含糊写入；下一分钟任务根据持久失败状态重试。上述预算不是生产容量或传输耗时结论。

## 一致性、秘密和短期正文

部署命令先停止 app，等待 #23 的正常退出，再由备份 CLI 取得 `control/operation.lock` 和与 app 完全相同的 `data/service.lock`。整个跨库读取、当前策略维护、快照重写、节点外上传和收据写入均持有锁。app 停止后所有配置、报告库、collection 库、可选 GitHub 库和活动兴趣配置组成一次边界；配置及权利状态在上传前、后再次比较，改变时删除这次对象并失败。操作者更新配置、权利请求或运行其他写库 CLI，也必须在这个维护窗口/同一锁下操作；不能旁路启动第二个写者。`observerctl` 的启停、恢复与备份、watchdog 共用宿主 control lock，避免看门狗在备份期间重启 app。

普通备份使用 SQL schema + 逐行 INSERT 重建全新的 SQLite 页面，安装原索引和触发器，保留 `sqlite_sequence` 高水位；不复制运行中 DB/WAL/SHM 或 SQLite freelist。原始数据库的签名表及设备/配对表仅检查 schema，不查询其内容行。快照直接跳过 `private_access_meta`、`devices`、`device_pairings` 和 `pairing_rate` 的全部数据；signing_key 不曾进入普通备份文件。环境、Owner/API/SMTP/S3 凭证、备份 AES key、TLS、Agent tmpfs、日志和任意目录均不在文件清单内。

保留报告库中的 Report Record/Canonical MD/PDF BLOB、archive/sync 序列、父子版本、更正/撤回关系、发布 outbox、通知/投递/对账身份与终态；保留 collection 的策略高水位、source_suppressions、来源提案/缺口元数据，及 GitHub context/momentum/repromotion 所需库与索引原字节。仅接受已知 application_id/user_version，以及当前 context schema 2、momentum schema 1；恢复必须使用清单指定的同一 application release，较新清单/数据库/索引版本 fail closed，不交给旧代码自行迁移。

不备份可重采原文：collection evidence、correction_source_evidence、HTTP validators、社交冻结样本、Agent 临时事件行均跳过；scheduled snapshot 在 INSERT 到新文件之前清空原文 Evidence Bundle 与 social samples，保留任务、版本、配置、评分/排序版本及发布结果身份；未完成冻结任务标记 failed，候选 correction payload 清空，未完成候选标记 blocked，保留去重身份。它们不会因进入备份而延长 SourcePolicy TTL。备份中这类任务没有继续原研究的授权输入；恢复后应按新的业务窗口收集，不能伪称原冻结输入可重放。永久报告引用仍受其原有永久归档许可与 #22 权利规则约束。

重写后再维护/VACUUM，避免被清理的候选字节留在空闲页。本地只创建自己登记的 staging 目录；正常成功/失败清除此目录。进程被硬杀后 staging 保持隔离，下一次同类受锁操作只清除 `snapshot-active.json` / `restore-active.json` 记录的准确自产目录，校验其父目录和受控名称；不枚举或清理任何旧 Owner DB、样本、容器、用户目录。已交付的恢复目录不自动删除，也不作为额外长期备份；季度演练结束后操作者应按当前来源策略处理该隔离数据环境，保留脱正文的演练记录。

## 自动触发与节点布局

安装 `backup.compose.yaml`、`backup.example.json`、`observer-backup.service`、`observer-backup.timer` 以及本版 `observerctl.sh` / `watchdog.sh`；保持 #23 的权限和不可变 release 安装方式。额外目录都由操作者预先创建，Compose 禁止隐式创建路径。control/restore 目录为 UID/GID 10001、0700；配置、authority 和秘密目录为 root:10001、0750，文件 0440；秘密不能放 config/authority 中。

| 宿主示例 | 备份容器 | 内容 |
| --- | --- | --- |
| `/etc/observer/backup` | 同路径，只读 | 私人 `config.json`，来自 backup.example.json |
| `/etc/observer/backup-authority` | 同路径，只读 | 备份之外保存的最新 `rights.json` |
| `/etc/observer/backup-secrets` | `/run/backup-secrets`，只读 | 独立恢复的 encryption-key、s3.json；演练时可临时提供 restore-owner-token |
| `/srv/observer/backup-control` | `/var/lib/observer-backup`，可写 | 持久收据、最后清单、最新契约、演练记录及自产 staging |
| `/srv/observer/restores` | `/var/lib/observer-restores`，可写 | 新命名的隔离恢复环境 |

备份容器只在命令执行期间运行，不挂 Docker socket、生产 Owner/Provider 秘密或 TLS。生产 app 不挂备份凭证/control 目录；其运行镜像含备份程序，但不因此获得 S3 凭证。`deployment.env` 新增的备份路径仅由备用 Compose 文件使用，不影响尚未配置备份的 #23 部署。

`encryption-key` 为秘密管理系统生成并独立保存的 32 字节随机值的标准 base64（44 字符），不从 Owner token/SMTP key 派生。`s3.json` 私人格式为 `{"accessKeyId":"<private>","secretAccessKey":"<private>"}`，需要时可带 `sessionToken`；SDK 不读取个人 AWS/Codex 配置，不走默认凭证发现。以上尖括号是说明占位，不是可运行凭证。初次无删除记录时，Owner 明确提供 schema1 `observer-rights-suppression` 的空 sources/versions 契约；缺失文件绝不当空。每次新的 #22 删除契约应同时保存到节点外独立 authority 管理流程，不能仅依赖这台节点的下一次备份。

配置 endpoint/bucket/region/prefix/expectedBucketOwner 并保持 `enabled:false`，实际准备好私有存储及独立恢复秘密后启用 `enabled:true`。此时执行以下命令会真正联系对象存储，属于授权环境操作：

```sh
observerctl.sh backup-status
observerctl.sh backup
systemctl daemon-reload
systemctl enable --now observer-backup.timer
```

timer 每次完成后约 60 秒检查一次（另有 5 秒 timer 精度），不依赖日报开关。`due` 对比上次成功快照的持久 cursor：新报告版本、PDF 状态、邮件事件高水位、权利标记、来源/兴趣/运行配置或 release 改变都会触发；没有这些变化时，默认每 12 小时生成跨库快照，配置不得超过 24 小时。成功收据仅在上传及边界复核成功后推进；失败/running 遗留状态下一次重试。正常成品检测约在下一次分钟检查，实际节点外完成还需退出、重写和上传耗时，不能把“分钟检查”声称成生产 RPO/SLA。

每次备份会短暂停止 API 与后台工作，代理仍在但可能返回上游不可用；结束后只恢复本次原本运行的 app。正常失败同样恢复原运行 app并返回非零，备份失败保持持久可见，不把业务停止当重试队列。被强制终止、节点崩溃或 Docker 故障时可能需要操作者显式 `backup` 重试及 `up`；timer 不擅自启动原本已停的服务。正常停止可能使在途研究重试、SMTP 变为 unknown；这是当前停机一致性协议的明确代价。真实暂停时长、07:30–08:30 窗口影响和邮件时序留 #26。

原生 Linux 入口为 `node dist/backup-admin.js --config /absolute/config.json due|status|create`；源码工作环境也有 `npm run backup -- ...`。`due` 返回 10 表示应备份、0 表示不需要，其他非零是错误；`create` 自己取得 flock，但操作者需先停止 app，否则非阻塞锁拒绝。不能把内部 `OBSERVER_BACKUP_LOCKED` 标志用于绕过锁。CLI 的 status 输出只显示时间/状态，不输出 cursor 中的私人配置。

## 删除、恢复和邮件去重

快照之外的 `authority.obs` 与本地 `latest-authority.json` 单独保存删除契约；新的备份读取并合并远端、本地、Owner 最新契约，不能因本机 control 丢失而覆盖较新的标记。来源同版更改/版本回退拒绝。#22 生命周期是权利判定/清理权威；来源策略或契约变化后，在新快照上传前删除旧 snapshot 对象，只保留清理后的新对象。维护失败也尝试删除旧快照；删除失败保持 failed，不能报告撤销完成。上传期间同一服务锁阻止旧 staging 与本节点删除操作并发，配置/标记变化会被边界复核发现。私有加密不替代删除。

干净恢复的每一次 invocation 必须提供**真实事故/演练起点**（毫秒精度 UTC），以及备份之外的最新 SourceConfiguration 与 #22 契约；不是只拿旧 snapshot 内的删除表。`currentSourcesPath` 是独立取得的最新来源文件，默认示例指向已审运行 sources.json；在干净节点应先从最新配置/权利管理来源提供它。明确的 `sources:[]` 是 Owner 权威空配置，读取失败/缺失则失败。程序合并远端与 Owner 契约、应用最新 SourcePolicies、永久标记与跨库清理，完成后才生成可启动目录；操作末尾再次读取两类 authority，变化则失败。

恢复阶段不开 HTTP、不构造 Provider、不发送 SMTP。只能在新的 drill ID 目录建立 staging，不覆盖或合并既有数据库；完整 AEAD 认证、清单文件尺寸/校验、数据库/索引版本、报告 ID 清单、SQLite integrity/foreign-key check、最新删除维护和邮件围栏均成功后，才原子重命名为最终目录。缺对象、错误 key、损坏/截断/校验失败、未知版本、最新 authority 缺失或变更、清理失败均不产生可启动的部分新环境。源码/依赖升级必须先回到清单要求的 release，再按独立升级流程迁移。

示例为操作入口，时间由操作者记录，不能照抄过去时间当真实事故：

```sh
observerctl.sh restore drill-2026q4 <incident-utc-with-milliseconds>
```

产出位于宿主 `/srv/observer/restores/drill-2026q4/{data,config}`，带 `manifest.json` 与 `restore-receipt.json`。切换前冻结原写者，准备与 snapshot 完全相同的应用镜像和适合该节点的独立秘密。受控 stop 后把 `OBSERVER_DATA_DIR` / `OBSERVER_CONFIG_DIR` 指向这个新目录，再 `up`；保留原数据，不清空原库。恢复配置采用固定的容器数据路径，日报、采集、PDF 生成、邮件、更正、巡查均关闭；报告/已有 MD/PDF 的鉴权读取仍可用。配置/删除权威若在 restore 后、首次启动前有变化，应使用最新输入重做新 ID 恢复，不能直接启动陈旧待恢复目录。

所有 Owner/Provider/SMTP/API/下载相关秘密从独立秘密管理输入恢复，TLS 使用独立证书恢复/重新签发流程。新服务首次启动生成新的 signing_key 和 epoch；devices、未消费 pairings 均为空，旧设备 credential_digest 没有恢复，因此必须重新配对；旧下载签名和 sync cursor 也失效。不是仅更换 signing key 后仍允许旧设备。

原通知 ID、delivery ID、RFC Message-ID、accepted/delivered/unknown/bounced/rejected 及对账身份保持；sending 转 unknown，未发送 pending/preparing 转 suppressed。快照可能漏掉其边界之后的 SMTP 受理，恢复库持久写入 `recovery_mail_fence`：恢复业务日及之前的任何历史报告（包括以后重建的缺失版本）禁止自动进入 pending/preparing/sending；未来业务日可按新配置正常投递。于是重新运行不会自动重发历史已完成邮件，也不声称找回 RPO 窗口里已丢失的受理回执。需要解决历史未知投递时沿用 #19 独立证据对账，不移除围栏或盲目补发。

## 测量与季度演练记录

RPO 目标 ≤86400 秒：操作者记录的事故/演练开始时间减去这次成功获取、完整验证的 snapshot `boundaryAtUtc`。起点应在恢复环境、凭证、DNS/镜像等准备之前保存，不能等材料齐全后重新起表。快照缺失、晚于事件起点、不能认证/恢复、取不到最新权利输入均失败；本地 lastSuccess 仅是上传收据，不替代干净环境读回证据。

RTO 目标 ≤14400 秒：同一个已记录事件起点，直到**该 snapshot 对应的实际运行服务**通过 Owner 鉴权 ops（所有后台开关关闭）、archive，以及最新可见业务日各可用 MD/PDF 的读取完成。它包含已计时的节点/镜像/秘密/配置准备、下载、解密、验证、清理、受控启动与就绪检查。staging 完成时只有 `NOT_MEASURED / ready-for-private-start`，不能记 RTO PASS。

私有服务运行后，从恢复时独立提供的 Owner token 文件完成最终事件；备份容器允许这里的 `http://app:3000` 私有 Compose 网络入口（普通公网 HTTP 不允许），`/v1/ops` 仍不能经 Caddy 公开：

```sh
observerctl.sh complete-drill drill-2026q4 http://app:3000 /run/backup-secrets/restore-owner-token
observerctl.sh backup-status
```

`/v1/ops` 的 `storage.recoverySnapshotId` 必须与本次实际恢复 UUID 一致，不能用仍在运行的原节点健康响应替代。就绪失败记录时间并保持待检查状态，重试不重置事件起点；已完成记录不能重用相同 drill ID。没有任何可读产物的空库/纯墓碑演练即使数值满足目标，也记 INCOMPLETE，不能作为报告恢复 PASS。RTO 数字只涵盖所记录环境和实际检查范围，不包括模型/来源联网、真实收件或生产容量资格。生产授权后才可按 #26 流程重新启用未来工作。

每季度用新的 `drill-YYYYqN` ID 重复上述 restore、受控私有启动、complete-drill 流程。`control/drill-<id>.json` 持久包含 schema、事件/请求/清理/结束时间、phase、snapshot/release/configuration ID、RPO/RTO 目标与实测秒数、readiness 失败时间、检查范围及 verdict；无完成事件的 running/ready 记录是未完成，failed 为失败，不能用上季度数字代替。实例规模、Node/S3/权限配置和目标节点需由 #26 一并冻结并引用，当前没有这些实测输入。这里没有增加故障矩阵、损坏样本或自动创建部署的测试框架。

## 本票验证与未测范围

依赖通过 `npm install --ignore-scripts --no-audit --no-fund` 安装并更新锁文件，没有执行依赖脚本。2026-09-08 块末唯一 `npm run typecheck` 返回 1，仅报告 `backup-s3.ts` 的 SDK credentials.sessionToken 与 exactOptionalPropertyTypes 不匹配；随后改为显式构造 credentials，并只在 token 有值时添加该字段。此集中窄修仅静态核对，未重跑类型检查，因此最终候选不能标为 typecheck PASS。没有新增测试、夹具、capture、hash 验收、全量/旧集成回归或 Docker 执行。真实 S3 API/私有权限/删除、跨库退出与恢复、加密损坏识别、进程中断清理、设备重配对、邮件历史围栏、季度演练、RPO/RTO 和生产容量全部 **NOT VERIFIED**；实现中的失败分支不能替代这些类别的运行证据。

依据第一方资料：S3 [PublicAccessBlock](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetPublicAccessBlock.html)、[PolicyStatus](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketPolicyStatus.html)、[版本化状态](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketVersioning.html)、[DeleteObject 的版本化语义](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html)、[Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObjectLockConfiguration.html)；SQLite [VACUUM 与删除页面清理](https://www.sqlite.org/lang_vacuum.html)。这些说明协议机制，不构成本项目实测通过。

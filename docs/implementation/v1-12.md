## 公共入口与兼容

Request 8 → Record 9 / ReportVersion 8 / `observer-canonical-v7`。请求仍是严格解析的六栏输入，不接受调用者/Agent 自报 GitHub 数字、历史、分数或函数。`createObserver` 的 `github` 由受信观察模块装配；缺少新能力产生本栏 Gap，不从旧七项里冒充完整排名。

同一个观察 Module 新增 `rankingSnapshot(cutoffUtc)`，返回严格 `GitHubRankingSnapshot` schemaVersion 2，先在全部截止前合格样本中择样，保存当前有限候选最多 50 项，再由 Heat 选择最多 7 项。原 `snapshot` schemaVersion 1 的 cap 7、顺序和旧正文路径不改。`authorize` 明确区分两种真实收据。

Request 1–7 / Record 1–8 / Version 1–7 / Canonical v1–v6 沿用旧规则，算法不会重写旧刊。两库均不迁移：报告 SQLite user_version 1；观察 SQLite application_id 1329746759 / user_version 1。新算法只改新 Heat 排名的 tie-break，不连带改变旧观察数组的既有顺序。

固定 API、same-node 详情身份、未知风险隔离、来源与凭证生命周期、逐跳路由/DNS 守卫、secondary 403 有界读取以及当前失败禁止旧好样本复活，全部继承 [V1-11](v1-11.md)。不新增网络路径；metadata 只使用当时详情中的 language / createdAtUtc / topics，null 与明确空数组不互补，不从未来详情回填。

## 深模块与保存输入

公开重算入口为 `rankGitHub({ snapshot, interestProfile, history, algorithmVersion })`，可直接独立 import，不要求预加载 Observer。它是无 I/O、无时钟读取的确定性纯重算；不是授予出版权限的入口。生产的 history 只能由真实报告库导出，纯重算参数不能注入 `produce`。

Record 9 保存原 `github` v2 收据、既有 `interestProfile`、`githubRanking`。后者包含固定规则及公式说明、历史实际刊物引用/Record SHA/可证 node/来源依赖、全部合格候选的总序/分数/系数/cohort/选择结果，以及 `unranked` 缺样/隔离原因。原始收据不在 Ranking 里复制第二份。有限集合之外的搜索截断只作 Gap，不制造未知项目的评分。

重算先校验配置/观察 ID 摘要、实际时间、身份历史摘要及所有完整候选择样；第 8–50 项、未选项、隔离项也与实际保留收据匹配。不是对已保存的得分再次 hash 自证。归档还验证编辑投影、版本/Record/正文摘要及重算结果；读取历史依赖时再次核对真实旧刊的 node、日期、发布时间和完整来源列表。公式字符串只用于解释，绝不 eval/动态执行。算法规则的任何变化必须使用新版本及新归档路径，保留 v1 解码与重算，不原地变更已有评分依据。

```ts
const report = observer.readReport(versionId, ownerCredential);
if (report.record.schemaVersion === 9) {
  const { github, interestProfile, githubRanking } = report.record;
  const replay = rankGitHub({
    snapshot: github, interestProfile, history: githubRanking.history,
    algorithmVersion: githubRanking.algorithmVersion,
  });
  // replay 与完整 githubRanking 逐字段一致。
}
```

## `observer-github-heat-v1` 精确规格

下述参数来自 [固定输入比较](v1-12-parameters/README.md) 后的工程选择，不是历史研究例子的 API/算法常量，不是统计校准的质量或用户满意度估计。UTC 毫秒与实际双点间隔参与计算；一天 = 86,400,000 ms。

1. **输入资格与分区。** 只有观察模块的 measured / cold-start 进入评分，missing / quarantined 单独保存原因且不占位置。创建时间必须存在且不晚于当前实际观察或 cutoff，否则 `invalid-age`、年龄 unknown，不把负年龄截成“新仓库”。实测和冷启动各自比较，最终 measured 分区在前、cold-start 在后，不能用巨大冷启动存量压过实测分区。
2. **信号与注意力下限。** measured 的 stars/forks 信号分别为 `max(0, signedDelta) * dayMs / actualIntervalMs`，至少一个实际净变化为正才合格；累计存量不进入实测分数。负/零原始 delta 和两点时间原样保存，平均速率不声称精确事件流水。cold 信号分别为 `stock / max(1, ageDays)`，下限为 stars ≥ 10 或 forks ≥ 2，并显式标记存量/年龄代理，不冒充实测动量。下限衡量观察到的关注，不承诺代码质量或安全。
3. **cohort。** 仓库年龄在 cutoff 计算，区间 `[0,30)`、`[30,365)`、`[365,+∞)` 天。先按分区+language+age；样本数 < 4 回退同分区+age，仍 < 4 回退整个同分区。null language 保持未知但可以形成自身 cohort，不猜语言。cohort 成员是全部观察合格且年龄有效的候选，包含稍后因关注下限、topic、冷却或历史 Gap 被排除者；先固定比较总体，后做编辑过滤。保存精确 memberNodeIds 和 fallback；小样本降低精度而非保证某语言入榜，4 不是统计显著性门槛。
4. **分位与基础分。** `P(x)=0` 当 x≤0；否则 `P(x)=(count(peer<x)+0.5*count(peer===x))/n`，并列取中位秩。正信号 singleton 为 0.5；全零为 0。`base=0.60*P(starsSignal)+0.40*P(forksSignal)`。不同 cohort 的分位刻画相对位置，不保证总体规模变化时排名不变。
5. **显式兴趣。** 仅按当前详情 topics 与冻结 Interest Profile 的 topics 匹配，复用既有 key 规范化；匹配项中最大 priority∈[0,100] 带来 `1+0.15*priority/100` 倍率。明确排除 topic 则不合格。topics null 保持未知、[] 明确空；二者均不凭空授予兴趣提升。阅读语言、地区和实体不作为编程语言筛选或临时语言配额。
6. **历史衰减。** 最近实际报道距离 cutoff 的 elapsed ≤ 7 天时普通冷却且恢复 0；之后 `clamp((elapsed−7天)/30天,0,1)`，第 37 天全恢复。近 90 天实际刊次 `c` 的频率倍率为 `1/(1+0.25*c)`。最终原分 `base*interestMultiplier*recoveryMultiplier*frequencyMultiplier`；年龄无效、未达关注下限、topic 排除、历史不明时为 0。资格按未量化的原 score>0 判断。
7. **稳定总序。** measured 在前；同分区按 `sortKey=Math.round(score*1e12)` 倒序；再按 opaque node ID 的 Unicode 码点逐位升序（前缀较短优先）。这是可传递的固定整数排序键，不是成对 epsilon。保存原 score 与 sortKey；数学 0.45 的二进制尾差不能抢在 node tie-break 前。sortKey=0 不等于原 score=0，7 天后 1 ms 的正资格不会被量化抹去。
8. **实际配额。** eligible 取原 score>0；novel 指过去 30 天未报道。`N=min(7, eligibleCount, 2*eligibleNovelCount)`；按上述序先保留前 `ceil(N/2)` 个 novel，再按 eligible 总序填到 N，最后按总序输出 chosen。对实际最终入选数再断言 novel≥ceil(actual/2)。3 个合格 novel 只支持最多 6 项；只有 1 项时要求其 novel；novel=0 则空栏。不添加低质量项目凑数，不用“先按目标7保留3”漏掉奇数上取整。
9. **理由。** 逐项保存 primary reason：history-unavailable → invalid-age → topic-excluded → cooldown → attention-insufficient → selected → novelty-quota/capacity（优先次序固定）。`selection` 区分 novelty-reserved 和 rank-fill。未选且本可进入无配额前 7 的项目为 novelty-quota；原本就在普通前 7 之外为 capacity，不能将所有低排名落选都归咎配额。全部分量仍可解释多个同时存在的因素。

### 历史的因果、权限与事务

历史只来自 `reports` 中成功 INSERT 的不可变刊物；Record 8 的实际 Watch Item、Record 9 的 selectedNodeIds 记报道。失败、预览式纯重算、重复 INSERT 冲突都不记历史。名称和 URL 不用于匹配，已验证稳定 node 在改名/转移后继承历史。

历史在本次 produce 首个 await 前冻结，须为较早 businessDate，且实际 publishedAtUtc / 旧 evidence cutoff 均不晚于本次 cutoff。未来发表的旧业务日回补刊不倒灌。窗口统一 `(cutoff−D, cutoff]`：恰 30 天视作 novel，恰 90 天不计频率/历史依赖，恰 7 天恢复仍为 0；测试区分 ±1 ms。

同一 node 在同一成功版本最多计一次；当前仅允许每 businessDate 的不可变 v1，重复请求不能形成第二刊次。后续更正/撤回/Re-promotion Event 的身份与计数由后票另订，不在此引入版本去重猜测。旧 Record≤7 的 GitHub prose 在相关 90 天窗内没有可证 node，明确 `github-history-unavailable`，不默认 novel 或从链接猜身份。

相关历史存在权限撤销或完整性问题时，本栏保存 `unavailableVersionIds` 并暂停普通选择。可信且已在 90 天窗外的旧刊先淘汰，其失权不永久挡住新刊；旧刊本身的读取鉴权不放宽。完整性损坏的旧刊不能证明自己的时间，保守记历史不明，不从损坏字段断言已过 90 天。Request 8 的其他栏目不从损坏刊物复用事实、指纹或事件链接，并使用既有 legacy-history-unclassified 披露历史不完整；旧 Request≤7 原 fail-closed 行为不改。

最后使用同一报告库的同步 `BEGIN IMMEDIATE`：重新导出历史并核对冻结输入、重核当前观察授权，然后 INSERT/COMMIT；变化或冲突 ROLLBACK。观察库不被长事务锁住，无两库写事务。不能在并发旧刊成功后提交过时的新颖性决定；调用者可以重新 produce 冻结最新可信历史。历史来源永久留存/衍生分发及读取权限仍被精确校验，不凭自报 policy 列表替代真实依赖。

## 执行循环

1. **选 frontier**：将 manifest 的计划边与 GitHub 原生关系列表核对，再逐个确认前置票已合并到集成基线且验收通过。聚合 blocked_by 计数仅作提示，本次观察到它与实际关系暂不一致；不能仅凭零计数、子 agent 回复“完成”或 Issue 被关闭就解锁下游。
2. **判断外部就绪**：开发票可用可控来源/进程/交付替身测试；live gate 的账户资格、来源许可、凭证、费用、收件人及资源操作需已授权。缺少外部条件则标明等待，不降格成模拟 PASS。
3. **派发 fresh context**：一个 subagent 负责一票、一个独立分支/worktree；并发受可用槽位与冲突边界限制。提供下面的最小任务包，不复制整段需求聊天。
4. **保护共享契约**：V1-01 固定最小共有数据/Runner 契约；公共 Schema、迁移序列、发布状态或通用接口变更由 orchestrator 协调单一写入者。确需联动时先合入兼容契约，再让相关 worktree 更新基线。
5. **审核并集成**：逐条核对 Acceptance criteria、业务演示、失败用例及测试类型；记录未覆盖边界。合入后在新的集成提交重新执行受影响检查，证据绑定代码/配置/输入指纹，再把票标为完成。
6. **推进或交接**：每完成一票重新计算 frontier，不等固定“阶段”整批结束。当前无可执行票时保存准确的已合并提交、剩余阻塞与下一检查点，不重复报告泛泛“继续”。

### 最小任务包

- 规划 ID、真实 tracker ID、票体全文及验收项。
- 基线提交、专属 worktree/分支、允许修改范围；公共契约的当前版本及协调负责人。
- 先读 [领域词汇](../../../CONTEXT.md)，再按票中参考分支经 [阅读路由](README.md#按需阅读路由) 加载 PRD/ADR/研究。
- 已完成依赖的契约变化和相关验证证据；跨票共享产物以仓库现态为准。
- 完成回报：实现的外部行为、逐项验收结果、精确测试命令和证据、代码提交、未验证/外部条件、是否改变共享契约。

单个 subagent 只完成自己的票，不因为发现下游工作就扩大范围、自动合并别人分支或关闭兄弟票。产品运行时的六个 Research Agent 与开发 subagent 是两种角色。

## 长期评测的交接方式

V1-27 启动独立持久调度，产物绑定冻结批次；agent 会话无需持续在线。V1-28 还要满足 14 个连续真实业务日和人工事实核查条件，不能仅因 V1-27 已完成就自动宣告可验收。

下一次会话带批次 ID、当前指纹、已完成日期、缺失核查与下次检查点即可继续。用产品提供的定时/监控机制或受控服务运行，不让工具阻塞等待多天。期间版本变化按已冻结评测规则处理，故障日不能删除或补造。

## 完成语义

- 开发完成：V1-01–25 的相应业务路径与自动化验收通过。
- 真实环境就绪：V1-26 的独立实测通过，可用 Provider 范围明确。
- 评测已启动：V1-27 的批次持续运行，尚不代表质量合格。
- V1 资格通过：V1-28 的真实 14 天和人工核查满足 PRD 阈值；单 Provider 按 PRD 限范围声明。

Android UI、无 GMS 真机验收、推送与公网运营都不在此 V1 执行范围。正式自动生产切换仍需 Owner 授权；任何以上状态都不能替代授权或来源许可。
